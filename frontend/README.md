# زوار موضوع | Mawdoo3 Visitors — frontend

React 19 + TypeScript ~6.0 + Vite 8 single-page app (PWA-capable), in Arabic (right to left, the default) and
English. Design contract: `../docs/initial-assessment.md` (§10 frontend, §7 security, §8 API). Phase
decisions: `../docs/decisions/` — the brand, the languages and the design system are in
`phase-10-frontend.md` (the product name, mawdoo3.com's palette and the kit of direction C: F10-27 on);
the platform owner's area and a company's e-mail texts are in `phase-11-frontend.md`; a company's own
identity (its logo and colour on every page of its people and visitors, the product's name and logo in the
platform owner's area only) is in `phase-12-frontend.md`.
The development guide (`../docs/development.md` §2.4 and §2.5) has the language conventions, how to add a
string in both languages, and the design tokens with their contrast rules.

Run it after a backend schema change (the backend test `tests/unit/test_contract_snapshot.py` fails until you do); `src/types/api.contract.test.ts` then shows every place `api.ts` must follow. |

`VMS_API_PROXY_TARGET` overrides the proxy target for `dev`/`preview` (e.g. an E2E backend on its own port). Both servers have CORS disabled: the app reaches `/api` same-origin through the proxy.

## Conventions

- **Every text a person reads comes from the catalogs** (`src/i18n/locales/{ar,en}/<namespace>.json`): `const { t } = useTranslation('visits')`, then `t('detail.title')`, `t('common:actions.close')`, `t('list.count', { count })`. Add a key to the English catalog *and* the Arabic one (Arabic plurals need `_zero`, `_one`, `_two`, `_few`, `_many`, `_other`); keys are type-checked and `src/i18n/catalogs.test.ts` checks completeness (and that Arabic has no Latin words but UTC and QR: put names, e-mail examples and key names in `{{variables}}`). English text stays as it is (tests read it). `src/i18n/hardcodedText.test.ts` and `logicalProperties.test.ts` scan every source under `src/` (tests excepted); a file that must keep a literal or a physical class goes into the test's `ALLOWED` map with the reason.
  - Text built outside a component follows the language at the moment it is read: module-level label tables use `lazyTexts({...})` (getters) or a function, never a string computed at import; a key built from data (an enum code from the API) goes through `catalogText(ns, key)`, which returns null for an unknown code so the caller can fall back. A sentence with elements inside (a count kept whole, a link, an e-mail address) is one catalog sentence split with `withParts` (React) or `textWithParts` (plain text), so each language orders its own words.
  - A 422's field errors carry a code (`details.field_codes`, backend B10-18): `translateFieldError` (`src/i18n/fieldMessages.ts`, used by `useFormErrors`) shows the server's English message in English and the `errors:fieldCodes.<code>` text, filled with the code's parameters, in Arabic; a code the catalog does not know keeps the server's words. A new backend code needs a text in both catalogs (`fieldMessages.test.ts` compares them with the snapshot's `field_error_codes`).
- Format dates, times, numbers and durations only with `src/utils/datetime.ts`, `number.ts` and `duration.ts`: they follow the UI language (Levantine month names, Latin digits in Arabic). A component that formats calls `useTranslation()` or `useLanguage()`, so it re-renders when the language changes. Error messages come from `getErrorMessage` / `ApiErrorMessage` (translated by error code).
  - Line breaks: an Arabic date keeps its day, two-word month and year together (no-break spaces), and a time range never breaks at its dash: build ranges with `joinTimeRange` / `joinSpacedRange`, never with a bare `–`. A sentence that names a moment uses `momentOnDay` and has a key for the same day (`{{time}}`) and one for another day (`{{date}}`, `{{time}}`), so Arabic never puts «الساعة» before a date.
  - Items of data in one line (a host and a department, a company, contact details) go through `DataLine`, which isolates each one (`<bdi>`): two values in the other script must not merge into one run.
  - Arabic: a sentence whose subject is a person's name has no verb or adjective that agrees with a man («أُلغيت بواسطة {{name}}», «سبق تسجيل دخول {{name}}»); checking in is «تسجيل الدخول» (`catalogs.test.ts` checks both terms). The audit log has words for every metadata key and value the backend writes (`auditVocabulary.test.ts` reads the backend's source).
- **Right to left**: use logical classes only (`ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`/`text-end`, `rounded-s`/`rounded-e`, `border-s`/`border-e`), never left/right, on screen and in print variants; give directional icons (arrows, chevrons, sign in/out) `mirror-rtl`; wrap Latin-only values in Arabic text (codes, e-mail addresses) in `dir="ltr"` (phone numbers: `PhoneNumber`). SVG charts take the UI's `direction` and mirror their geometry (marks through a transform, texts by their x, never the texts themselves); arrow keys follow the direction time runs.
- The default colours are mawdoo3.com's (`index.css`, every ratio noted and checked by `src/designTokens.test.ts`); a company with a colour of its own has its palette in their place (see "Whose page it is"). In the default colours the shell is `theme-shell` (side-nav teal; `theme-shell-deep` in the dark scheme and around a dark screen), the platform owner's shell `theme-shell-platform` (the deep teal; mawdoo3's slate, `theme-shell-slate`, in the dark scheme, where a company's shell is the deep teal: the two are never the same colour), the content area light greys with slate text, the whole app dark in the dark colour scheme. A screen that is dark from edge to edge (the reception tablet) declares `handle: DARK_SURFACE_HANDLE` on its route (`layouts/shellSurface.ts`); a dark panel inside a light page uses `theme-dark` (or `Card`/`StatTile` `variant="emphasis"`). Turquoise and the yellow are fills behind ink text, never a colour for white text.
- **The appearance (phase 13).** Each device chooses Light, Dark or System (the default: the device's own `prefers-color-scheme`, followed live), in `localStorage` (`vms.appearance`), one choice for every company and the platform owner's area. The scheme it draws the page in is `data-scheme="light|dark"` on `<html>`: `public/appearance.js` (a classic script in `<head>`, before the stylesheet; the policy allows no inline script) puts it there before the first paint, `startAppearance()` keeps it there (a choice, another tab's choice, the device's own scheme under System). **One switch**: every rule that means dark goes through the `scheme-dark` variant (`@variant scheme-dark { … }` in `index.css`, `scheme-dark:` on a class; screen only, paper stays light), and script that chooses something by the scheme (a logo's file, the browser chrome's colour, a preview) reads `useColorScheme()`. Never `@media (prefers-color-scheme)` or Tailwind's `dark:`: `appearance/appearance.test.ts` fails on them. A screen that is dark by design (`DARK_SURFACE_HANDLE`, the reception) stays dark under System and Dark and is light for Light (`useShellSurface`). The switch is a radio group of three (sun, moon, monitor) beside the language switch on the signed-out pages and the pass (`AppearanceSwitch`), and a group of `menuitemradio` in the account menus (`Menu`'s `radio-group` entry).
- No explanatory notes (brand pass, decision 3): no page or card descriptions, no time-zone sentences, no empty-state sentences; facts go in `PageHeader`'s `meta` (a `MetaLine`). Errors, validation, data, counts and password rules stay.
  - `MetaLine` never leaves a separator dot at the end or the start of a wrapped line (each fact carries its dot before it and the line clips the first one of every row), and a fact with a direction of its own (`dir="ltr"`: a slug, an address) that wraps keeps its lines on the reading side (`text-align-parent`, a utility in `index.css`; Chromium knows `match-parent` only by its prefixed name).
  - A value shown where a form would have a field (an account's address beside the password to hand over) is a `ReadOnlyField` (text in a box that grows), never a read-only `Input`: an input shows one line and cuts a long address off on a phone.
  - A control's accessible name starts with the words on it (WCAG 2.5.3): "Edit default text: Subject (Arabic)", "Send reset link to Nadia Haddad". Two links that go to different places have different names ("Audit log" in the navigation, "This company's audit log" on a company's page).
- **Whose page it is (phase 12).** Every page shows one identity, resolved by `useIdentity()` (`identity/identity.ts`): the product's in the platform owner's area (`/platform/…`), the signed-in company's, the company a signed-out address names (`/c/{slug}`, `?c={slug}`), or nobody's (neutral). Put `IdentityLockup` where a page shows whose it is (the shell, the signed-out pages, a printed sheet's header) and end titles with `useDocumentTitle` (the company's name in the UI language; nothing on a neutral page). Never import `BrandLockup`, `BrandLogo`, `BRAND` or `useProductName` outside the platform owner's area: they render nothing there anyway, and `components/app/productBrandGuard.test.tsx` fails on the import, on the product's name in a catalog or a source, and on anything of the product in a rendered page of a company or of nobody.
  - A company's colour reaches the page as its palette (`BrandPalette`, derived by the server): `identity/tokens.ts` maps the palette's roles onto the tokens of `index.css` (`--color-accent: var(--brand-light-accent, #188086)`), for the light and dark content, the shell and the deep shell, and `IdentityController` sets the `--brand-…` properties on the root element through the CSSOM (the style policy allows no inline style). Components keep using the semantic tokens and need to know nothing of it. A token that a brand should colour gets a `var(--brand-<set>-<token>, <default>)` value in `index.css` and an entry in `BRAND_TOKEN_NAMES`; `identity/tokens.test.ts` holds the two in step and computes the contrast of every text and background pair for the server's own palettes (`src/test/serverPalettes.json`), awkward colours, a colour grid and random palettes. Status colours never follow the brand.
  - **A company's own colour is on its surfaces.** The shell and the filled buttons are the palette's `surface`: the colour as it was chosen wherever white or the dark ink reads on it (a yellow company is yellow, under dark ink; a navy one navy, under white), with `on_surface` as the ink and `surface_hover` as the step. `accent` is therefore a **fill under `on-accent`** and nothing else (`identity/accentUse.test.ts` reads every source for another use): a line or a mark in the brand's colour on the content area (a chosen option's border, a native checkbox, a meter) is `accent-strong`, and coloured text `accent-text`, which stay the step that shows on white. On the shell nothing is a fixed white: its texts, the current page's pill (`bg-accent text-on-accent`: the ink with the shell's colour as its text), its dividers (`border-border`: the ink laid thinly over the shell), its hover fill (`bg-surface-muted`), the signed-in user's tile (`bg-highlight`) and the focus ring all read the shell's tokens, so build anything that stands on the shell from those. A fill that would blend into a white card gets an edge (`ACCENT_FILL_EDGE` in `buttonStyles.ts`, on every element with `bg-accent` that is a control), and a shell that would blend into the canvas a line (`border-shell-edge`). The dark colour scheme and the dark reception screen keep the deep and bright steps.
  - A logo for light surfaces stands **on a white plate** wherever the surface is not white: on the shell (whatever its colour: a company's colour is its logo's, and a logo drawn on its own colour disappears) and on the signed-out pages (so a logo with a background of its own looks meant). The logo for dark surfaces is drawn only on dark surfaces: a dark shell, the deep shell, the dark colour scheme. A logo about as wide as tall (an emblem) has the company's name beside it (`CompanyLogo` measures the file once it has loaded; pass `nameBeside={false}` where the name already stands next to it).
  - Links between the signed-out pages keep the company (`withCompany(path, linkSlug)`); a redirect to the sign-in page goes through `signInPath()` / `loginPath()` (`auth/redirect.ts`), which lead to the page of the company this device last signed in to. The visitor's pass asks the server for the public brand of the company its link names and nothing else, with `credentials: 'omit'` (`api/publicBrand.ts`); the token never leaves the fragment.
  - A brand is never drawn as it arrives: `parseCompanyBrand(value, slug)` / `parsePublicBrand` (`identity/brand.ts`) keep an image address only when it is the public brand endpoint's **for that company's own slug**, a colour only with a palette that keeps the contract's guarantees, and a name only when it is plain text. That holds for the API's answers and for the device's copy alike; always pass the company's slug.
  - The device remembers its company and the brands it has seen in `localStorage` (`vms.company`, `vms.brands`; validated on every read, and replaced by the server's answer on every load) so a page starts in the right colours (`applyBootIdentity`, before React renders); a company the device has never seen (a visitor's first pass) is asked for before the first render, for at most 800 ms (`primeBootIdentity`), so nothing is painted in the default colours first. On a connection slower than that the page is drawn in nobody's colours (`PENDING_PALETTE`, the slate of the app's text) until the company's arrive, and a page's colours are always replaced at once, never faded (`applyDocumentIdentity` switches transitions off for two frames). The signed-out pages follow the device's company: `/login` leads to its sign-in page, `/forgot-password` and an older `/reset-password` link to themselves with `?c={slug}` (`useRememberedCompanyAddress`; never carry a location's fragment along: a reset link's is its token). `index.html` is neutral: no product name, the neutral icon, no manifest.
- Server state lives only in TanStack Query; UI state in `useState`. No other global store.
- All dates are shown and entered in the company timezone (`me.company.timezone`) via `src/utils/datetime.ts`; never the browser's.
- The company is named through `useCompanyName(me.company)` (`src/i18n/useLanguage.ts`): its Arabic name in the Arabic UI when it has one, else `name`. Never render `me.company.name` directly.
- A department is named the same way, through `useDepartmentName()` (`src/i18n/departmentName.ts`; `departmentDisplayName(department, language)` outside components, `compareDepartmentNames(language)` to sort): its `name_ar` in the Arabic UI when it has one, else `name` (the English name). Never render `department.name` directly: `src/i18n/departmentNameGuard.test.ts` type-checks `src/` and fails on any read of a department's `name` outside that module and the department dialog's form logic (`features/admin/departmentForm.ts`). Names people type (visitors, hosts, companies, purposes) are shown as typed.
- Components use semantic design tokens from `src/index.css` (`bg-surface`, `text-fg-muted`, `bg-accent`, `text-accent-text`, `bg-attention`, `bg-highlight`, `bg-emphasis`, `bg-row-highlight`, tone, `status-*` and `chart-*` tokens, `font-numeric`, `text-page`, `text-section`, `text-meta`, `text-kpi`, `rounded-card`/`rounded-control`), never raw palette colors.
- Status is always icon + text (`StatusBadge`), never color alone. Interactive widgets follow the WAI-ARIA APG patterns.
- New routes go into the owning feature's `routes.tsx` with a `RequireRole` guard from `SECTION_ACCESS`; link with `paths` from `src/paths.ts`.
- Pages stay thin: form state, validation and mutations live in `features/<feature>/` components and hooks (auth mutations: `src/auth/useSessionActions.ts`), as in `features/auth/*Form.tsx`.
- Forms: pure validators return `FormErrors` (`src/utils/forms.ts`); `useFormErrors(mutation.error, { fields, codes })` merges them with the server's 422 field messages (map every field to its server path, e.g. `visitor.email`), returns `formError` for the alert, and focuses the first invalid control after a failed submit. Spread `form.field(name)` on the `Field`.
- Buttons: put `loading` on the button that started the action; it stays focusable (`aria-disabled`) and ignores activation. Use `focusableWhenDisabled` for a button that can become unavailable while focused. Plain `disabled` only for buttons that are unavailable before anyone can focus them.
- Sources are UTF-8 without a BOM; invisible characters (BOM, zero-width, bidi controls, non-ASCII spaces) are written as `\uXXXX` escapes. `config/sourceEncoding.test.ts` enforces both.
- **Two principals, two sessions (phase 11).** A company's users sign in at `/login`; the platform owner at `/platform/login`, with cookies of its own, and a browser may hold both. Everything of the platform owner is under `features/platform/` and `/platform/…`: `PlatformRoot` (its 401/403 reactions, tab sync and language), `RequirePlatformAuth` (a company session does not count), `PlatformLayout` (a shell of its own colour, `theme-shell-platform`, with the "Platform" / «المنصة» label). The two never mix:
  - the API client sends the platform CSRF cookie for `/platform/…` requests and the company's elsewhere (`csrfCookieNamesFor` in `api/client.ts`);
  - every platform query and mutation key starts with `queryKeys.platform` (`['platform', …]`); `auth/session.ts` leaves those alone and `features/platform/platformSession.ts` touches only those, so a sign-out or an expired session of one principal never clears or redirects the other;
  - `AuthProvider` ignores errors of `/platform/…` requests and never navigates a platform page; `safeNextPath` refuses platform pages, `safePlatformNextPath` accepts only them;
  - pages below `PlatformLayout` get `SessionOwnerContext` (`platform:<id>`), so `useUrlParams` / `useBackLink` never ask `/auth/me`; the language switch there saves through `PATCH /platform/auth/preferences` (`usePlatformChangeLanguage`). Dates on platform pages use the device's time zone (`platformTimeZone()`): the platform owner belongs to no company.
- **A company's e-mail texts** (`/admin/email-templates`, administrators; the UI says "Email texts" / «نصوص الرسائل»): `emailTemplateForm.ts` mirrors the server's checks (`checkTemplateText`, the backend's `check_text`: same order, same field codes) so problems show while typing with the `errors:fieldCodes` texts; the server's 422 lands on the same fields (`ar.<field>` / `en.<field>`). The draft is previewed with `POST …/preview` (subject and text version); the saved e-mail is shown faithfully by `<iframe sandbox src="/api/v1/email-templates/{kind}/preview?language=…">` (`emailTemplatePreviewUrl`): never put the returned `html` into the page (`style-src 'self'` strips its inline styles, and it is not the app's markup).
  - The editor is laid out by field: a field's Arabic and English texts are one group, side by side from `md` and one right under the other on phones. Each text has its variables under it at all times, as a toolbar (`useRovingToolbar`: one tab stop, arrow keys in the reading direction, Home/End); on touch screens the row scrolls sideways. Nothing appears or moves when a text takes focus.
  - The draft's text version is split into its language sections (`previewTextSections`: the leading language's, the other's under its name between two rules, the footers by their own letters with isolated values left aside); each section is set in its direction and carries its `lang`, whatever script a name in a line has. "Send test" sends with the language the preview shows first.
  - The rules of the variables come with the template, not from constants of the SPA: `EmailTemplate.variables` and `max_variable_uses` (a variable at most that many times in one text) and each field's `required_variables` and `forbidden_variables` (the purpose of a visit is not a variable of a subject). A text's chips are `fieldVariables(field, template.variables)`: what the text may not hold is not offered. A message that names a variable shows its translated label ("“Purpose” cannot be used in this text."), never the raw name, also when the server refused the text (`serverProblemMessage`). A saved text that today's rules refuse (saved before a rule existed; the e-mails use the default text in its place) shows its problem from the start, not only once it is typed in (`refusedSavedTexts`).
  - The default texts have one name in each language: "default text(s)" / «النص الأصلي», «النصوص الأصلية». Do not introduce a second one ("the product's texts", «نصوص المنتج»).
  - The same list and editor serve the platform owner for any company (`/platform/companies/{id}/email-templates`, phase 12): they read where their data comes from and where their links lead from an `EmailTemplatesSource` (`features/admin/emailTemplatesSource.ts`; the company's own endpoints by default, `platformEmailTemplatesSource(company)` under `/platform/…` with the platform's query keys). A new behaviour of the editor goes into the shared components, never into one of the two pages.
- **A company's identity, set by the platform owner** (`/platform/companies/{id}/identity`, "Identity" / «الهوية»; a company's own administrators have no such control). The logo, the optional logo for dark surfaces and the square app icon are prepared **in the browser** (`identity/imagePipeline.ts`): whatever image is chosen is decoded through an `<img>`, the empty room around the drawing cut away, drawn on a canvas inside the contract's limits and encoded as PNG, and only that PNG is uploaded (`PUT …/brand/assets/{kind}`, the file as the body). The chosen file's own bytes never leave the device, and a file the browser cannot decode is refused there. The colours offered come from the logo's pixels (`extractColours`); the preview is drawn with the palette the server derives for the colour in the field (`POST /platform/brand/palette`, debounced), on the app's own classes (`useTokenScope`). Pictures and the colour are a draft until *Save identity*; removing a saved picture and resetting the colour act at once, after one line of confirmation.
  - A picture is checked **for the place it is chosen for** (`prepareLogo(file, ground)`), since nothing else says so before the company's people see it: a logo for white backgrounds that is nearly all near-white is refused there with the place it belongs in (`too-light`; the mirror, `too-dark`, for the logo for dark surfaces), and so are a strip wider than 8:1, a column taller than 1:2 and a raster picture under 96 px on its longer side. A picture without transparency on a flat white background (every JPEG) loses that background, from its edges inwards (`clearFlatBackground`: what the drawing encloses stays); a background of another colour is left alone, since it may be the logo's own tile. A new refusal is an `ImageProblem` with a text in both catalogs (`platform:identity.problems`).
  - The app icon follows the logo: a logo that fits a square is put on a white tile (`iconFromLogo`); a wordmark (wider than 2:1), which is a speck in a browser tab, gives the first letter of the company's name on its `surface` colour (`letterIcon`, the letter in the name's own script), drawn again when the colour changes. Where the icon came from is the page's memory for one visit (`IconOrigin`): an icon saved earlier is never redrawn, and one chosen by hand is left alone. Removing the logo removes the icon with it, unless it was chosen by hand during the visit.
  - The three pages of the platform about one company (its identity, its e-mail texts, one e-mail's texts) are headed by the company's logo tile and name (`PageHeader`'s `leading` and `subject`), and name it in the tab's title.
- **Waits.** A wait the server names (`Retry-After` of a `429 RATE_LIMITED`) is read with `rateLimitWaitSeconds(error)` (`api/client.ts`; null when the error is another one or the server did not say) and said in words with `formatWaitDuration` ("Try again in 25 minutes." / «حاول مجددًا بعد 25 دقيقة.»), rounded up to a whole minute; the short forms of `formatDuration` ("25m") are for figures. The test e-mail, an administrator's reset link, *Add company* and *Add administrator* do this; without the header the server's own message stays.
- **Background refreshes.** A request sent with `backgroundRefresh: true` carries `X-Background-Refresh: 1`, and the server does not count it as activity, in both realms: an idle session must end although its tab keeps asking. Mark only the later fetches of a query that keeps itself fresh (`isBackgroundFetch`: the session's re-check by the heartbeat or on returning to the tab, the reception's polled lists); never a query's first load, a list a person opens or filters, or a mutation. On the platform's routes the only marked request is the re-check of `GET /platform/auth/me` (`features/platform/platformSessionExpiry.test.tsx` holds that), and a re-check that finds the session ended takes the tab to `/platform/login?next=…`.
- `useFormErrors` also has `refresh(clientErrors)` and `attempted`: after a refused submit, re-check on change (`if (form.attempted) form.refresh(validate(next))`) so a message goes when its field is right; `refresh` never moves focus.
- `ApiError.retryAfter` holds a 429's `Retry-After` seconds (null when the server did not say).
- Tests mock the API with `mockApi` (`src/test/api.ts`). A request without a matching route fails the test after it ends, naming the method and path, even when the UI swallows the error. The QR decoder module (`src/scanner/zxing.ts`) is replaced by an inert fake in every test (`src/test/setup.ts`); decoder tests opt out with `vi.unmock('./zxing')`. The setup also emulates the browser's focus fixup (a focused element that becomes disabled loses focus), which jsdom lacks. What an effect sets after the commit (the document title of `useDocumentTitle`) is asserted with `await waitFor(...)`, never read at once after a `findBy…`: the effect may not have run yet.
- List pages keep their view in the URL (`?tab=&q=&page=`): read it with `useUrlParams` (`readEnumParam`, `readPageParam`) and change several parameters in one navigation; `useSearchInput` debounces a search box into `?q=`. Links from a list to a detail page pass `backLinkState(...)`, and the detail page's `useBackLink` returns to that exact view.
- Render code that depends on the current time (today's company-local date, "Today"/"Tomorrow") takes it from `useNow()`, never `Date.now()` during render.
- The one-time pass link (`pass_url` from creating a visit or resending its invitation) lives only in component state while the page shows it: never in the URL, browser storage or the query cache. The mutations that return it use `gcTime: 0`, so the mutation cache drops it as soon as the form or dialog that sent the request unmounts. `PassActions` (copy, QR code, print) is the only place that shows it; printing puts only the pass on paper (`[data-print-pass]` rules in `index.css`).
- Actions on a visit or visitor appear only when the resource's `permissions` allow them; roles decide navigation, never what may be done to a record.
- Page tests use the fixtures in `src/test/fixtures.ts` (`makeVisit`, `makeVisitor`, `page`, …) and fake only the clock (`vi.useFakeTimers({ now, toFake: ['Date'] })`) so debounces and queries keep real timers; polling tests use `shouldAdvanceTime` with `vi.advanceTimersByTimeAsync`.
