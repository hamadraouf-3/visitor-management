# Phase 9 — Frontend: production-readiness round 1

Date: 2026-10-06 · Scope: `frontend/src`, `frontend/public/sw.js`, `frontend/config`, `frontend/vite.config.ts` (not `frontend/e2e`, `playwright.config.ts` or the Dockerfile) · Contract: `docs/initial-assessment.md` revision 2, §10 (PWA, visual design, WCAG AA) and §15

The readiness audit reported seven frontend findings: two about what the browser downloads (service worker, entry chunk) and five accessibility findings from its keyboard, touch-target and reflow sweeps. Each was reproduced first, against a production build of the code as it was (`vite preview`, with a seeded API), using the audit's own method. All seven were real; none was rejected. Each was then measured again on the fixed build. Each entry: **decision** — reason, then the tests and the measurements. "Before" and "after" are the same script on two builds served side by side.

Checks at the end: `npm run typecheck`, `lint`, `test` (105 files, 1146 tests) and `build` pass. The full Playwright suite also passed with these changes (177 passed, 10 skipped by their project conditions). It ran from a copy of `frontend/` on its own ports (5291, 8792) and its own database, so the E2E owner's runs were not disturbed. The suite runs the Vite dev server. The last change, keeping the stylesheet out of the `app` chunk group (F9-2), affects only `vite build`, and came after that run. It was checked again on the production build with the browser scripts.

## Downloads

F9-1. **The service worker downloads only what changed, and the visitor's pass page does not install it (finding: SW downloads every asset twice and the whole app again after each deploy, low).** — Reproduced: on a first visit to `/login` the worker fetched every file again with `cache: 'reload'`, including the files the page had just loaded. Every deploy re-downloaded everything, the 1 MB zxing wasm included, because the cache name changes with each build. `/pass` registered it too.
   - `src/pwa/registerServiceWorker.ts`: `shouldRegisterServiceWorker(pathname)` is false for `/pass` (matched with the router's `matchPath`, so `/pass/` and `/PASS` count too). Visitors open their pass on their own phones and never use the staff app, so their phones never download it. A device that already has the worker (a staff member's) keeps it on every page. All other pages register it as before (production builds only, `updateViaCache: 'none'`).
   - `config/serviceWorkerPrecache.ts`: the manifest has a third list, `immutable`, of the bundle's files in `build.assetsDir`. Their names carry a content hash, and nginx serves `/assets/*` as `immutable` (phase-9-deploy D9-09). A public file is never in that list, even inside `assets/`. The version hash now covers `sw.js` as well, so a changed worker never shares a cache name with the previous one.
   - `public/sw.js`, on install: a hashed file is taken from this version's cache (an interrupted earlier install), else copied from an older `vms-precache-*` cache (same URL, same bytes), else fetched with the default cache mode, so the HTTP cache can answer for files the page just loaded. Files whose URL does not change with their content (`index.html`, the web manifest, icons) are always fetched with `cache: 'reload'`, as before. Activation still deletes the older caches, and the fetch handling is unchanged. `cache.addAll` was all-or-nothing; now one failed download still fails the install. The active version then keeps serving, and the retry keeps what was already stored.
   - Kept as the contract says (§10, "precache built static assets incl. the zxing wasm"): staff devices still precache the wasm. Because it is copied forward, it is downloaded once per zxing version, not once per deploy. Precaching it only for reception users, as the audit also suggested, would change the contract. It is not needed for the cost the finding measured.
   - Tests: `config/serviceWorker.test.ts` runs the real `sw.js` in a `node:vm` context against an in-memory Cache Storage and network. It checks a first install (hashed files `default`, the others `reload`, each fetched once), an update (unchanged hashed files copied, `index.html` refetched even though the old cache has it, old cache deleted on activate), and a failed download followed by a retry. All three fail against the previous `sw.js`, because the requests differ. `config/serviceWorkerPrecache.test.ts` checks the `immutable` list and that a changed worker gets a new version. `src/pwa/registerServiceWorker.test.ts` checks `/pass` (no `load` listener, no registration), `/login` (registers on load) and development (nothing).
   - Measured with an nginx-like static server that logs every request it serves (D9-09 cache headers), in a cold Chromium context. Byte counts are uncompressed. Before: the first `/login` visit made 32 requests, 2,655 KiB, 709 KiB of it files fetched twice. A deploy that changed one page fetched 2,207 KiB, the wasm included. The visitor's `/pass` made 35 requests, 2,681 KiB, and left a worker and a cache on the phone. After: the first `/login` visit made 87 requests, 1,984 KiB, no file twice. The same deploy fetched 58 KiB: the navigation, the worker and its manifest, the entry, the changed page, `index.html`, the web manifest and the icons. A deploy whose page change also adds a Tailwind class fetched 114 KiB, the stylesheet included. `/pass` made 12 requests, 516 KiB, with no worker and no cache.

F9-2. **Staff pages are lazy routes; the start-up chunks hold only the app shell (finding: entry chunk ships every staff feature, low).** — Reproduced: `index-*.js` was 268 kB raw / 78 kB gzip and held the admin, reports, history, evacuation and visit screens.
   - Every page of the admin, reports, history, inside, visitors and visits features is a `lazy: async () => ({ Component: (await import(…)).X })` route, as reception and pass already were. The auth pages (`/login`, `/forgot-password`, `/reset-password`, `/change-password`), the layouts, the guards and the router stay in the shell. Navigation entries (labels, icons) stay in each `routes.tsx`, so the menu still renders at once. A chunk that fails to load after a deploy shows the existing "A new version is available" boundary (`RouteErrorBoundary`).
   - `vite.config.ts`: a code-splitting group `app` (`isAppShellModule`, `tags: ['$initial']`) holds the shell's own modules, without `main.tsx`, `router.tsx` and the `features/*/routes.tsx` files. — Without it, every page chunk imported shared code from the entry chunk by its hashed name, and the entry holds the `import()` of every page. One changed page then renamed nearly every app chunk. Measured: a build where only `ReportsPage` changed had 53 new file names among its 75 assets. With the group, only `ReportsPage` and the entry changed. The stylesheet (`index.css`) is not in the group. Rolldown's file name for a chunk also covers the CSS that chunk owns, and the one Tailwind stylesheet changes whenever any page uses a new class. With the stylesheet in the shell chunk, such an edit renamed 61 chunks; with it beside the entry, only the page, the entry and the stylesheet. The group also moved Rolldown's CommonJS interop helpers into a `rolldown-runtime` chunk of their own. Before, the `react` vendor chunk imported them from the chunk holding `utils/cn.ts`.
   - Start-up set for `/login` (HTML, entry, modulepreloads, CSS): before 710.6 KiB raw / 208.5 KiB gzip / 176.2 KiB brotli, after 489.3 / 145.9 / 126.8. The entry is 10 kB, and the shell chunk 54 kB raw / 17 kB gzip. `date-fns` is no longer preloaded at start.
   - Tests: `config/chunking.test.ts` builds the app twice in memory, the second time with one statement added to `ReportsPage` and one rule added to `index.css`. It checks that no lazy page module is in the entry or any chunk the entry imports statically, that no page chunk imports the entry, and that only `ReportsPage` and the entry are renamed. Mutation-tested: it fails with the `app` group removed (page chunks import the entry), with the previous eager routes (13 page modules in the start-up chunks), and with the stylesheet inside the group (61 chunks renamed).
   - Unit tests: the files that render the whole app import `routes` from `src/test/appRoutes.ts`. It loads every lazy route module once, with top-level await while the file is collected, so a cold import never runs inside a `findBy` wait. That wait was the reason Phase 2–4 decision 2 kept the pages eager. `sessionToasts.test.tsx` no longer needs its own `beforeAll` import of the reception page. One test, `VisitorProfilePage.test.tsx` (SEC-28), now waits for the visit page's own back link: it had waited for a heading that both pages show (the visitor's name), and a lazy route renders a moment after the click. *(Amends phase-2-4-frontend decision 2.)*
   - Checked in the browser on the production build: every role opens every navigation entry, by client-side navigation and by direct load. Each shows its page heading, with no page error, no failed asset and the worker controlling the page.
   - After a deploy, a tab still running the previous version keeps working for every page whose chunk did not change: the new worker serves those URLs from its cache, where F9-1 copied them. A page whose chunk did change still loads while the browser's HTTP cache holds the old file. The previous worker's install fetched it there. Checked: after the v1 → v2 deploy, a tab left open on v1 loaded both an unchanged and a renamed page chunk. Once that copy is evicted, the old file is gone from the server, and the navigation shows the existing "A new version is available — Reload page" boundary. Before, that could happen only on `/reception`. It is not reloaded automatically, because a reload would drop a form being filled in (the walk-in, an invitation).

## Accessibility

F9-3. **The selected tab's focus ring is drawn inside the tab (finding: focus ring clipped by the scrolling tab list, medium).** — Reproduced: at 1440 and 820 the ring changed only 1 of 4 sides (a 2 px bar), on /reception and /visits. The tab list has `overflow-x: auto`, which clips the global ring drawn 2 px outside the tab. `Tabs.tsx`: `focus-visible:-outline-offset-4` on the tabs, so the ring is a rectangle inside the tab, above the selected tab's underline. In the phone grid layout (`phoneLayout="grid"`, `max-sm:overflow-visible`) nothing is clipped, so it applies only from `sm` and the segments keep the outer ring. Measured: the audit's pixel diff of the tab box ±6 px, focused against blurred. At 1440 and 820 it now changes 4 of 4 sides, all at ≥ 3:1 (6.2:1), on /reception and /visits. At 390 it stays 4 of 4 with the outer ring.

F9-4. **The scroll padding under a sticky action bar is the bar's measured height (finding: focus hidden behind the sticky Save bar on Company settings at phone width, WCAG 2.4.11, medium).** — Reproduced: at 390×844, Tab put "Notify the host when their visitor checks in" entirely under the 157 px stacked bar, because the page reserved only 96 px. At 320×640 the "Address" field was hidden the same way. New `components/ui/StickyActionBar.tsx`, used by the company settings and the walk-in form, holds the bar's shared classes. It measures its border box with a `ResizeObserver`, so a safe-area padding change counts too. It publishes the height as `--sticky-actions-height` on `<html>` (the tallest bar if there were ever two), and removes it on unmount. `index.css`: `scroll-padding-bottom: calc(var(--sticky-actions-height, 5rem) + 1rem)` while such a bar is on the page. That is the bar plus room for the focus ring, and it follows the layout, the text size and the zoom. Measured: the audit's Tab walk (4 long forms, at 320, 390, 820 and 1440) found 5 fully hidden stops before and none after. A stricter check (any part of the control or its ring under the bar) shows the settings form clear at every width. One stop comes close: at 320×640 the walk-in's "Purpose" field can stop with its bottom 2 px under the bar, so it is still not hidden. Tests: `StickyActionBar.test.tsx` covers publish and follow on resize, the border box being observed, removal on unmount, two bars at once, and no `ResizeObserver`. *(The "2 px" understated what was left: text areas and segmented radios could stay partly under the bar. See F9-8.)*

F9-5. **Controls on the dark camera panel get a white focus ring (finding: 2.76:1 focus ring on Start camera / Try again, WCAG 1.4.11, low).** — Reproduced on "Start camera", and on "Try again" too, which the audit could not render (`getUserMedia` stubbed to reject with `NotReadableError`): the indigo-600 ring was 2.76:1 against slate-900. `CameraView.tsx` sets `--color-focus` to white on the panel (`[--color-focus:var(--color-white)]`), so every control in it, present or future, uses the global `:focus-visible` rule with a white ring. The "Turn camera off" button's own `focus-visible:outline-white` is now redundant and removed. Measured on all three: white ring, 17.8:1, all 4 sides, at 1440, 820 and 390. "Turn camera off" was checked over a live canvas stream.

F9-6. **Touch targets of 44 px for the invite radios and the text links (finding: some targets below 44 px on tablet and phone, low).** — Reproduced with the audit's method (`elementFromPoint` through the target's centre, so labels and `::after` count, `pointer: coarse`): radios 24 px, table links and standalone links 20 px.

   - Table row links (`tableStyles.ts`): in the table layout on a touch screen the primary cell is `relative`, and the link's `::after` covers the cell, a row tall. Below the stacking breakpoint the card-wide link is unchanged. Interactive content in the same cell already sits above it (`relative z-10`, e.g. the evacuation list's phone link).
   - Standalone links: "Forgot your password?", "Back to sign in" and the visitor profile's mailto link are `inline-flex` with `pointer-coarse:-my-3 pointer-coarse:py-3`, which is 44 px with the layout unchanged, as `PhoneLink` already does. The visit page's "Visitor" link is followed by the company line, so it reaches 12 px up over its term (`-mt-3 py-3`) and moves the company 12 px down on touch screens only.
   - Not changed: the skip link (keyboard only), and the report chart bands, which have the "Show table" equivalent (the audit's own exceptions).
   - Measured, 13 cases at 390, 820, 1180×820 and 1440 (touch): 26 targets under 44 px before, none after. Radios are 324×64 (phone) and 718×46 (tablet). Table links span the cell (216–408 px wide, 62–145 px tall). Standalone links are 44 px tall. A tap on the radio's description now selects it (it did not before). axe (WCAG 2.2 AA tags) finds no violations on 11 pages that show these changes, at 390 and 1440. The radios' accessible names and descriptions were read from the accessibility tree.

## Re-audit round 1

The accessibility re-audit reported two low findings in this area. Both were reproduced first on a production build of the code as it was, with the audit's seeded data and its scripts, and both were real. Each one also turned up a related case that the finding did not list. Those cases were fixed too. "Before" and "after" are the same script run on the two builds, served side by side (`vite preview`, one API, one throwaway database).

F9-8. **A focused text area, or the segment of a segmented choice, is scrolled fully above a sticky action bar (finding: text areas only partly scrolled above the bar, low).** — Reproduced: at 320×720, Tab from "Email domain" scrolled the page 4 px. "Address" was left at 516–606 px, with the bar's top at 563, so 47 of its 98 px (ring included) were under the bar. At 320×580 the walk-in "Purpose" field had 23 of 74 px under the bar. The cause is the one the audit gave: Chrome scrolls a text area's caret line into view, not its box. Two cases the finding did not list have a similar cause. (1) The walk-in "Reason details" text area (shown for the reason "Other") had 23 px under the bar at 320×580, 320×720, 390×700 and 430×640 when Tab reached it partly in view. (2) The segmented radios of the walk-in ("Expected to stay", "Reason for the walk-in") hide the radio itself (1 px) and draw its ring on the label. The browser scrolls only the 1 px radio into view, so in a sweep of 6 widths × 20 heights, 17 of 240 radio stops left a segment up to 14 px (ring included) under the bar. F9-4 reported only a 2 px case, because its walk covered four viewport sizes.
   - `StickyActionBar.tsx`: while a bar is on screen, one document `focusin` listener (added with the first bar, removed with the last) checks the newly focused element in the next animation frame. That is after the browser's own focus scroll and before the frame is painted. The checked box is the element, or for a visually hidden control (1 px or less) the label around it, plus 4 px for the ring. If a bar covers that box, it is scrolled into view with `scrollIntoView({ block: 'nearest' })`, which honours the measured `scroll-padding-bottom` (F9-4). "Covers" means the bar itself is on top there: when a dialog lies over both, nothing moves. Two things are left where the browser put them. A control taller than the room between the scroll paddings (the walk-in tab panel, 1,387 px) is not moved, because aligning one of its edges could scroll its focused part away. Focus from a click or a tap on the control or on its label does not scroll either. The browser does not scroll for that, and moving the page under a pressed mouse button would select text. The pointer-down target is recorded for this check, and any key press clears it. Programmatic focus, such as the first invalid field after a click on "Save", is revealed like Tab.
   - Why the next frame, and not the `focusin` handler itself: the browser scrolls after it dispatches the focus events. Scrolling first would replace Chrome's own placement of an off-screen field (centred) with `nearest`. A frame callback runs before that frame is painted (HTML "update the rendering"), so the in-between position is never shown. Checked: an `IntersectionObserver` created on `focusin` gets its first entry in that first rendering update. On the fixed build, every entry reported the control and its ring clear of the bar. A script that reads positions right after the key press, as the audit's height sweep does, still sees the browser's own position, so it must measure one animation frame later. Run unchanged on the fixed build, that sweep still reported Address at 516–606 at 320×720.
   - Tests: `StickyActionBar.test.tsx`, 6 new cases. They cover: a text area left partly under the bar is revealed on Tab and on focus after a click; a hidden radio's segment is revealed; the ring counts; a control clear of the bar, one inside it, one taller than the screen and one under a dialog are left alone; a click or tap on the field or its label does not scroll, and the next keyboard focus does; the listeners are added once for any number of bars and removed with the last one, and a pending check is dropped. Mutation-tested: the tests fail without the reveal, the label lookup, the ring margin, the "bar is on top" check, the room check, the pointer exception, or the listener removal.
   - Measured, settings and walk-in. The audit's height sweep (6 widths 320–430 × 39 heights 560–940, 468 walks) was changed to measure one frame after each Tab, and the first-frame observer was added. That gives 5,850 focus stops per build, with the ring counted as 4 px, a stricter test than the audit's 2 px. Before: 134 stops partly under the bar and none fully hidden. These were "Address" 45 times (at most 47 px), "Purpose" 60 times (at most 23 px) and walk-in segments 29 times (at most 14 px). In every one of these cases, the first painted frame already showed the overlap (observer ratio as low as 0.48). After: 0 partly under the bar, 0 fully hidden, and every first painted frame clear. The radio-segment sweep went from 17 of 240 stops to 0. A Tab walk at 320×720, 390×700, 320×580, 320×640, 360×720, 375×700, 412×690 and 430×680 (two roles on the walk-in) found 25 stops partly under the bar before, 9 of them text areas, and 0 text areas after. The other 16 stops in both builds are the walk-in tab panel, which is taller than the screen. A Shift+Tab walk gives the same results on both builds. A click or a tap on the partly covered "Address" field leaves the page where it was, on both builds.

F9-9. **The evacuation list's visitor link keeps a band at least 44 px tall above the visitor's phone on touch screens (finding: visitor link 42 px on touch table layouts in rows with a visitor phone, low).** — Reproduced at 1180×820 with touch: in rows with a company line, the name link's tap area holds no square larger than 42 px, as reported. Without touch, and in the card layout, nothing changes: the row heights on /inside at 1440 without touch, and of the cards at 820 and 390, are identical on both builds.
   - Tests: `InsidePage.test.tsx` checks that the class is on the name block in a row with a visitor phone and that a row without one has no class there.
   - Measured on /inside, 4 touch viewports (1180×820, 1024×1366, 1366×1024, 1440×900) × 3 roles (reception, admin, management), 27 rows, 8 of them with a visitor phone (2 without a company). Before, rows with a company had a largest square of 42 px at 1180 and 1024 and a centre cross 42 px tall at every width. Rows without a company had squares of 22–69 px and a cross 23 px tall.    - Measured on every row, every pixel row of the name: after the fix no row loses any, at 320, 390, 768, 820, 1024 and 1440, with touch and with a mouse.
