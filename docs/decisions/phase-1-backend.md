# Phase 1 — backend decisions

Date: 2026-10-05. Scope: backend foundation (`backend/`). Each entry records a deviation from, or an
interpretation of, `docs/initial-assessment.md` (revision 2), with the reason. Nothing here changes the
API contract in §8/§8.1 except where explicitly stated.

## Schema (§4)

| # | Decision | Reason |
|---|---|---|
| B1-01 | `audit_logs` has **no foreign keys** (`company_id`, `actor_user_id`, `entity_id` are plain UUIDs). | An audit write must never fail because of the state of the rows it describes (e.g. a denial whose own request work was rolled back). §4 lists no FKs for this table; reads use LEFT JOINs. |
| B1-02 | Added `visits.invitation_requested boolean NOT NULL DEFAULT false`. | §8.1 defines `needs_attention` as "latest invitation FAILED (or NOT_SENT **with `send_invitation` requested**)"; without storing the request this cannot be computed. Avoids a schema change in Phase 3. |
| B1-03 | `updated_at` exists on business tables (companies, departments, users, visitors, visits, email_messages). Lifecycle tables (`user_sessions`, `password_reset_tokens`, `visitor_passes`, `audit_logs`) carry `created_at` plus their own event timestamps (`last_seen_at`, `revoked_at`, `used_at`, …). | Those rows only change through explicit lifecycle columns; an extra `updated_at` would duplicate them. |
| B1-04 | Extra CHECK constraints that only tighten §4: non-blank `name`/`full_name`/`purpose`; lowercase `companies.slug`/`email_domain`; `visitors.phone_digits` digits only; `cancelled_by_id`/`cancellation_reason` only on cancelled visits; `email_messages`: `attempts >= 0`, `(status='SENT') = (sent_at IS NOT NULL)`; enum CHECKs for `check_in_method`, `check_out_method`, `revoke_reason`, `kind`, `status`. | Defence in depth; every one is already implied by the contract's service rules. |
| B1-05 | The migration grants to the role named by `DB_APP_ROLE` (default `vms_app`, validated identifier) instead of a hard-coded name. `USAGE ON SCHEMA public` is granted on upgrade but not revoked on downgrade. | Deployments may use other role names. The schema predates the revision and `scripts/db.ps1` grants USAGE independently, so revoking it would break the provisioned baseline. |
| B1-06 | CHECK constraint names in the migration are wrapped in `op.f()`. | Alembic applies the metadata naming convention to `op.create_table`; without `op.f()` names doubled (`ck_users_ck_users_roles_valid`). A test now compares the migrated schema with `Base.metadata.create_all` (columns, defaults, constraint definitions, indexes) in addition to `alembic check`. |

## Errors and auditing (§7.4, §8.2)

| # | Decision | Reason |
|---|---|---|
| B1-07 | Failure/denial audit rows are written by the `AppError` exception handler (events attached to the exception; defaults: 403 FORBIDDEN → `ACCESS_DENIED`, 429 → `RATE_LIMITED`) through `audit.record_security_event` (own session, immediate commit). CSRF failures (middleware) and silently dropped forgot-password requests use the same writer. All of them pass through `SecurityAudit` (app state), which attributes events to the authenticated user and coalesces `RATE_LIMITED`/`CSRF_FAILED` (B1-33). | The handler runs after the function-scoped `get_db` rolled back, so the request rollback can never erase the event (also on the single shared connection of the test harness), and no 403/429 can be forgotten. |
| B1-08 | HTTP errors outside §8.2: 405 → `METHOD_NOT_ALLOWED`; other framework 4xx → `BAD_REQUEST` (original status kept). Database unavailable / deadlock / serialisation failure (`OperationalError`) → 503 `SERVICE_BUSY`. `GET /health` with the database down → 503 `SERVICE_BUSY` envelope with `details.database = "unavailable"`. *(Extended by B1-67: the CSRF middleware answers 503 `SERVICE_BUSY` as well when its session lookup cannot reach the database.)* | "Every non-2xx uses the envelope"; these are the closest contract codes. |
| B1-09 | `ACCESS_DENIED`, `RATE_LIMITED` and `CSRF_FAILED` metadata carry `{method, route}` with the full route **template** (e.g. `/api/v1/users/{user_id}`), or `route: "unmatched"`; never the concrete path. Unknown-account login failures are audited with `metadata.reason = "unknown_account"` (company/actor NULL, no identifier). *(Round 1 fix:)* templates come from `app.core.routing.route_template`, which uses FastAPI 0.142's public `fastapi.routing.iter_route_contexts` (effective routes, as OpenAPI generation does): after routing it identifies `scope["route"]`, before routing (CSRF middleware) it matches the path against every API route. This replaces prepending the API prefix and the raw path previously stored for CSRF failures. | IDs/enums only (§3.2-8); the path is attacker-controlled and carries IDs and arbitrary text. |
| B1-10 | *(Superseded by B1-33.)* Originally every `RATE_LIMITED` / `CSRF_FAILED` response wrote one audit row. | — |

## Authentication and sessions (§7.1–§7.3)

| # | Decision | Reason |
|---|---|---|
| B1-11 | Passwords are NFKC-normalised before hashing and verifying; change-password also rejects a new password equal to the current one. | Same password typed on different keyboards/IMEs must match; forcing a change from a temporary password must actually change it. |
| B1-12 | Hash concurrency = `PASSWORD_HASH_CONCURRENCY` (default CPU count); a request waits at most 2 s for a slot, then 503 `SERVICE_BUSY`. | §7.1 "saturation → 503" with a short grace period so brief bursts do not fail. |
| B1-13 | Login revokes a still-valid session cookie presented by the same browser before issuing the new session. | Prevents session sprawl on shared devices; harmless otherwise. |
| B1-14 | Session cookies carry `Max-Age = SESSION_MAX_AGE_HOURS × 3600` (aligned with the absolute server-side expiry). | Server-side expiry stays authoritative; the browser drops the cookie at the same time. |
| B1-15 | Password-reset invalidation sets `expires_at = now` on unused tokens; `used_at` is set only when a token is consumed. Reset validates the policy (422) **before** consuming the token, so a weak password does not burn the link. | Keeps `used_at` meaningful; better UX without weakening one-time use (consumption is the atomic `UPDATE … RETURNING`). *(Amended by B1-60: invalidation sets the new `invalidated_at` column instead of moving `expires_at`, so no later clock reading can undo it.)* |
| B1-16 | A temporary password that expires during an existing session does not block `POST /auth/change-password` in that session. | The session was established while the password was valid and lives at most 12 h. |
| B1-17 | Rate-limit thresholds are env-configurable (`RATE_LIMIT_LOGIN_PER_IP_EMAIL`, `…_PER_IP`, `…_PER_ACCOUNT`, `RATE_LIMIT_PASSWORD_CHANGE_PER_USER`, `RATE_LIMIT_FORGOT_PER_EMAIL`, `…_PER_IP`, `RATE_LIMIT_RESET_PER_IP`, `RATE_LIMIT_SCAN_PER_MINUTE`, `RATE_LIMIT_RESENDS_PER_VISIT_HOUR`, `RATE_LIMIT_API_PER_MINUTE`, `INVITATION_DAILY_LIMIT`; since B1-43 also `RATE_LIMIT_LOGIN_PER_PREFIX`, `RATE_LIMIT_FORGOT_PER_PREFIX`, `RATE_LIMIT_RESET_PER_PREFIX` and `RATE_LIMIT_MAX_ANONYMOUS_BUCKETS`); *(B1-66 replaced `RATE_LIMIT_MAX_ANONYMOUS_BUCKETS` with `RATE_LIMIT_MAX_NETWORK_BUCKETS` and `RATE_LIMIT_MAX_EMAIL_BUCKETS`, and `RATE_LIMIT_FORGOT_PER_EMAIL` now applies per existing account.)* windows are fixed as in §7.3. The account policy locks out for 15 min once reached. Limiter keys are HMAC-SHA256(SECRET_KEY, …) so no raw e-mail address sits in memory. | §7.3 "env-configurable". This is also what SECRET_KEY is used for. |
| B1-18 | `client_ip`: when every `X-Forwarded-For` hop is a trusted proxy the leftmost entry is used; an entry with a port (`1.2.3.4:80`) is invalid (→ NULL). A request from a trusted proxy address **without** `X-Forwarded-For` has no client IP (§7.3 "missing → None"): it is audited/logged with ip NULL and every such client shares one per-IP rate-limit subject (`unknown`). With the local `TRUSTED_PROXIES=127.0.0.1/32,::1/128`, direct calls to port 8000 (curl, `/docs`, a harness bypassing Vite) therefore look IP-less and share one budget; documented next to `TRUSTED_PROXIES` in `.env.example`. **Phase 9 note:** E2E traffic must go through the Vite proxy (`xfwd`), or set `RATE_LIMIT_ENABLED=false` for direct backend calls. | §7.3 leaves these cases open; none of the choices trusts an unverifiable hop. Falling back to the peer address would attribute every proxied request to the proxy. |
| B1-19 | `GET /departments?include_inactive=true` without the `ADMINISTER` capability → 403 `FORBIDDEN` (audited), not silently ignored. | "admin only" parameter; explicit denial avoids different semantics for the same URL. |

## Gate 1, round 1 fixes (2026-10-05)

| # | Decision | Reason |
|---|---|---|
| B1-31 | **Login throttles are reserved atomically.** `RateLimiter.reserve` takes one in-flight slot in the (IP, e-mail), IP and account buckets under one lock **before** the user lookup and the Argon2 verification; an in-flight slot counts against the limit until `settle` records it (failure) or gives it back (success, or no verdict such as 503). On success the (IP, e-mail) failures are cleared as before. The account lockout starts on the recorded failure that reaches the limit (`AUTH_ACCOUNT_THROTTLED` once). A bucket filled only by in-flight attempts answers 429 with `Retry-After: 1`. Forgot-password uses the same reservation (counted immediately). The unconditional `record()` was removed from the limiter so the check-then-record pattern cannot come back. *(Amended by B1-66: the account slot is taken in a second reservation, after the account lookup; the client's slots are still taken before it and before any hashing.)* | §7.1/§7.3 "rate-limit checks before any hashing": with check-then-record, N concurrent wrong passwords all passed the check (proved: 30 of 30 reached the verification). Now at most 5 per (IP, e-mail) and 10 per account are verified (`tests/integration/test_throttle_concurrency.py`). Operational note: more than `RATE_LIMIT_LOGIN_PER_IP` simultaneous logins from one NAT address briefly see a 1-second 429. |
| B1-32 | **Change-password throttle (not in §7.3).** Wrong `current_password` answers per user: `RATE_LIMIT_PASSWORD_CHANGE_PER_USER` (default 5) / 15 min, reserved before the Argon2 verification; beyond it 429 `RATE_LIMITED` with `Retry-After`. The failure that reaches the limit also **revokes the current session** (still answered 400 `INVALID_CURRENT_PASSWORD`; the audit row carries `session_revoked: true`), so whoever holds the session must sign in again, which needs the password and is subject to the login throttles. A successful change clears the budget. | Without it, anyone holding a session (an unattended shared reception tablet, §7.2) could brute-force the real password at the generic 600/min API limit and then take the account over. |
| B1-33 | **Deviation from §7.4 "one audit row per response" for `RATE_LIMITED` and `CSRF_FAILED`:** `SecurityEventCoalescer` writes the first event per (action, source, policy/reason) and 60-second window; repeats inside the window are counted and carried on the next written row for that key as `metadata.coalesced`; the response itself is unchanged (every request still gets its 429/403). The counts keep the volume visible to administrators. |

Audit rows and sessions keep the full address. | An IPv6 end site controls a whole /64 (RFC 6177); per-address keys gave it 2^64 fresh budgets (proved: 60 failures from one /64 → no 429). |
| B1-35 | **Reset-password throttle:** `POST /auth/reset-password` is limited per IP subject (`RATE_LIMIT_RESET_PER_IP`, default 20 / 15 min, every attempt counts), checked before the token lookup → 429 `RATE_LIMITED` with `Retry-After`. | Each failed lookup writes an `AUTH_PASSWORD_RESET_FAILED` row; the endpoint had no bound at all. Tokens are 256-bit, so this is about abuse volume, not guessing. |

Backstop: `sqlalchemy.exc.DataError` (SQLSTATE class 22, e.g. NUL in text) → 422 `VALIDATION_ERROR` with `fields.body`, logged as a WARNING without traceback. | PostgreSQL text cannot hold NUL: such input produced 500s with full ERROR tracebacks (log flooding) for what is a client error. |

## Phase 1 follow-up, round 1 (2026-10-05)

Fixes for the curated open findings B1-B19 of the second gate round. B19 (`--no-server-header`) is recorded in B1-27, the B16 amendment of B1-33 in B1-55.

| # | Decision | Reason |
|---|---|---|
| B1-43 | **Rate-limiter memory is bounded** (finding B5). A bucket carries its policy and is dropped as soon as nothing in it can affect a decision (no in-flight slot, no lockout, no hit inside the policy's own window): on settle when a reservation leaves nothing behind, and by a sweep that runs at most once per second of clock time, driven by the calls themselves, visiting buckets per policy in last-touched order and stopping at the first one still inside its window. A denied reservation creates no buckets. Policies keyed by anonymous input (login, forgot-password and reset-password: client addresses and digests of typed e-mail addresses) are marked `anonymous` and capped at `RATE_LIMIT_MAX_ANONYMOUS_BUCKETS` (default 100,000). At the cap, after an expiry sweep, **new** anonymous keys are refused: 429 `RATE_LIMITED` with `policy = anonymous_capacity` and `Retry-After: 60`, plus a WARNING at most once a minute (fail closed). Live buckets are never evicted, because evicting one would reset somebody's failure count or lockout (a bypass); authenticated budgets (per user, per visit) are not capped. New secondary limits per IPv6 /48 on the anonymous endpoints: `RATE_LIMIT_LOGIN_PER_PREFIX` 300 failures / 5 min, `RATE_LIMIT_FORGOT_PER_PREFIX` 100 / 15 min, `RATE_LIMIT_RESET_PER_PREFIX` 200 / 15 min (IPv4 clients have no prefix key; their per-IP subject is the whole client). Reset-password now reserves its (IP, prefix) slots and settles them as counted at once instead of calling `hit()`, so a capacity refusal is reported as such. *(Amended by B1-66: the single anonymous cap became two caps (network keys, typed e-mail keys), and a full cap no longer refuses anything: new keys of that scope are admitted untracked. `anonymous_capacity` is gone.)* | Buckets were kept for 24 h whatever their window (measured: 20,000 forgot-password requests left 40,000 buckets, about 40 MB, still held two hours later), the keys are attacker-chosen, and an IPv6 /48 (65,536 /64 subjects) could create tens of millions a day. The old sweep also walked the whole dictionary under the global lock. The prefix limits and the cap are additions to §7.3 (env-configurable like the others). |
| B1-44 | **Pass-token grammar shared with the frontend** (finding B1). `extract_pass_token` implements exactly the rules of `docs/contract/pass-token-vectors.json` (a bare token, or `http(s)://host[:port]/pass[/][?query]#<token>` without user info, spaces or ASCII control characters) with a plain pattern instead of `urlsplit`; `tests/unit/test_tokens.py` runs every shared vector, and its contradicting `/pass#…` case was removed. "Remove leading and trailing whitespace" is implemented as ECMAScript's `String.prototype.trim()` set (what the frontend parser uses), not Python's `str.strip()`, which also strips U+001C-U+001F (e.g. a trailing GS from a handheld scanner) and U+0085 and keeps U+FEFF; backend-only tests pin these differences. | §6: scanner input is parsed identically on both sides. Suggestion for the owner of the shared vector file: add cases for a trailing GS (`…\u001d` → null) and a leading BOM (→ token), so the frontend runs them too. *(Done in B1-64.)* |
| B1-45 | **Credential changes and logins serialise on the user row** (findings B2, B3). `UserRepository.lock_credentials` re-reads the user `FOR NO KEY UPDATE`, refreshing the loaded object. Login: after the Argon2 verification and before the session is created, the stored hash must still be the verified one (and the user still active and not expired); otherwise 401 `INVALID_CREDENTIALS`, audited as `AUTH_LOGIN_FAILED` with the new reason `credentials_changed` and counted like any failure. Change-password: after the verification, lock, then require the current session to still be live (otherwise 401 `NOT_AUTHENTICATED`, audited `AUTH_PASSWORD_CHANGE_FAILED{reason: session_ended}`) and the stored hash to be the verified one (otherwise 400 `INVALID_CURRENT_PASSWORD`, reason `credentials_changed`): a compare-and-swap, nothing is written otherwise. Reset-password locks the user row before it consumes the token, the same order as change-password (which locks the user and then invalidates that user's reset tokens), so the two cannot deadlock. `_set_password` flushes the users UPDATE before sessions are revoked. Deactivation already locked the row first. *(Extended by B1-62: issuing a reset token takes the same lock.)* | §7.2 revocation: a login or change that verified the old password before a reset/change committed must not survive it. Proved with two committed connections: the attacker's login session outlived the reset, and an in-flight change overwrote the reset password. `FOR NO KEY UPDATE` is the lock the UPDATE takes anyway and does not block foreign-key checks of rows that only reference the user (a new session). Tests: `tests/integration/test_credential_races.py` (they fail with the guards disabled). |
| B1-46 | **Security decisions use the route path** (finding B4). `app.core.routing.route_path(scope)` strips `root_path` exactly like Starlette's router (a unit test compares it with Starlette's private `get_route_path`). The CSRF/Origin middleware (the API-path check and the exemption list), the API response headers and the audited route template all use it; the access log keeps the full requested path. | With `uvicorn --root-path /vms` the raw `scope["path"]` is `/vms/api/v1/…`: the middleware skipped every check while the router still dispatched the request (fail open). `tests/integration/test_root_path.py` fails on the old behaviour. |
| B1-47 | **`APP_BASE_URL` and `QR_BASE_URL` are origins** (finding B6), normalised like `ALLOWED_ORIGINS` (lowercase host, default port dropped, trailing slash removed). A path, query, fragment or credentials is a startup error naming the setting. An empty `APP_BASE_URL` is an error; an empty `QR_BASE_URL` falls back to `APP_BASE_URL`. Documented in `.env.example`. | The SPA serves `/pass` and `/reset-password` at the root, and the pass grammar requires the path to be exactly `/pass`: `https://host/vms` produced QR codes the scanner rejects and reset links that 404. |
