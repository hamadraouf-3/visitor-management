# Phase 5 — Reception frontend: decisions and deviations

Date: 2026-10-05 · Scope: `frontend/src/features/reception`, `frontend/src/scanner` (+ tests) · Contract: `docs/initial-assessment.md` revision 2

Each entry: **decision** — reason. Items marked *(handover)* need an action outside this builder's folders. Numbering uses the prefix FR5.

No dependency was added. Nothing in `src/api`, `src/types`, `src/utils`, `src/components/ui`, `src/layouts`, `src/router.tsx` or `package.json` was changed: every endpoint, type and helper the screen needs already existed.

## Scanner: state machine and camera

1. **The §10 state machine is two parts combined.** — `scanFlow.ts` is a pure reducer for one pass (`ready → validating → result → acting → success → ready`); the camera hook owns `idle / starting / live / error`. `scannerPhase(flow, camera)` gives the §10 state: the flow's step while a pass is handled, otherwise `idle`, `starting` or `scanning` from the camera. A pass from the handheld field runs the same flow without a camera (camera denied, unsupported, or simply off). `useScanStation` composes camera, decoder, de-duplication, reducer and the mutations; a synchronous copy of the flow (`flowRef`) lets a detection and a server answer that arrive before React renders still see the current step.
2. **getUserMedia constraints.** — `{ video: { facingMode: { ideal: 'environment' }, width: { ideal: 1280 }, height: { ideal: 720 } }, audio: false }`. The size is only a hint (never fails), for a sharper picture of the code. A camera the user picked is requested with `deviceId: { exact }`, so the picker means what it shows; if that camera is gone (`OverconstrainedError` / `NotFoundError`) the request falls back to the default constraints and the stored choice is forgotten.
3. **Only an explicit camera choice is remembered** (`localStorage` `vms.reception.cameraDeviceId`, try/catch, `src/scanner/preferences.ts`). — The camera `facingMode` picks is not stored, so a device keeps following "rear camera" until someone chooses otherwise. The picker is shown only when there is more than one camera.
4. **Auto-start.** — Permissions API `granted`: start without a click. `denied`: show "Camera access is blocked" without prompting. `prompt`: "Start camera" button. Where the API cannot answer (Firefox before 131 and older Safari throw for `camera`), the camera auto-starts only if it has started on this device before (`vms.reception.cameraUsed`); this is the "permission was granted before" fact those browsers do not expose. A later permission `change` to `granted` (the user allowed it in the browser's site settings) starts the camera too. Auto-start happens only while the Scan tab is shown; "Turn camera off" disables it for the rest of the visit to the screen.
5. **One stream for the session.** — The camera hook lives at screen level, not in the Scan tab, so the stream stays open while the receptionist uses another tab (decoding pauses; no new permission prompt or camera start-up when they come back). Tracks are stopped on unmount (route change, sign-out), while the page is hidden (`visibilitychange` → hidden, `pagehide`) and restarted when it is shown again (`visibilitychange`, `pageshow`). A track that ends on its own (camera unplugged, access revoked) becomes "The camera stopped" with Try again. A `getUserMedia` answer that arrives after a stop, restart or unmount is stopped at once (generation counter).
6. **Camera error mapping** (`src/scanner/cameraErrors.ts`, pure). — `NotAllowedError`/`PermissionDeniedError`/`SecurityError` → blocked; `NotFoundError`/`DevicesNotFoundError` → no camera; `NotReadableError`/`TrackStartError`/`AbortError` → in use (Chrome on Windows reports a camera held by another process as `AbortError`); `OverconstrainedError` → unusable camera; `TypeError` → unsupported; anything else → generic. An insecure context is checked before `navigator.mediaDevices` (browsers hide it there, so it would otherwise read as "unsupported"). A decoder that cannot be loaded (preload or detector creation failed, e.g. CSP blocking wasm) blocks the camera with "The QR reader could not be loaded". Every message names the fallback (handheld scanner / paste) where the camera cannot help; Try again is offered only where it can.
7. **Decode loop** (`src/scanner/useQrDecodeLoop.ts`). — One `detect()` at a time, the next scheduled 160 ms later (about 6 attempts per second), only when the video has a frame (`readyState ≥ HAVE_CURRENT_DATA`). A frame that cannot be read is skipped (one warning logged). Turning the loop inactive stops scheduling at once and discards a detection still running. The detector (native `BarcodeDetector` when it supports `qr_code`, otherwise the self-hosted zxing ponyfill) is created once, on first use, after the preload started on mount.
8. **"Hold the code steady and closer"** appears after 8 s of scanning without any decode, restarts with every decode and every restart of scanning, and is announced. It is a hint, not an error: the camera cannot tell whether a code is in view.

## Scanner: de-duplication and input

9. **De-duplication applies to the camera.** — A detection is taken only while scanning (decoding pauses during a scan, a result, an action and the success state). The same pass is then ignored for 5 s, keyed by its token (the same pass as a URL or a bare token is one key, `detectionKey`), and every further sighting restarts the 5 s; the window is also restarted when scanning resumes after a result. A visitor who keeps holding up the code they just used therefore never triggers a second scan (otherwise the 5 s would often expire during the ID check and the next sighting would offer a check-out). It must be out of view for 5 s. Exactly one `/reception/scan` per detection (tested).
10. **The handheld field is not de-duplicated:** every Enter is a deliberate entry and is checked, also the same pass again; it can replace a shown result or the success state. Nothing is taken while a scan or an action is running.
11. **What is sent** (`scanPayload`). — A recognised pass (`parsePassToken`) is sent as its bare token. Anything else is sent as typed (trimmed, at most 4,096 characters, the `ScanRequest` cap of B1-49), so the server answers `PASS_INVALID` and audits the attempt (§6 row 1); the client never decides on its own that input is invalid. A blank field is never sent. The QR check-in/check-out sends the same payload as `pass_token`. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-23.)*
12. **Fine vs coarse pointer.** — Fine pointer: the field is always shown and takes focus whenever nothing else has it. "Nothing" includes the layout's programmatic landing targets (the `main` region and the page `h1`, which AppLayout focuses after navigation), and the check is deferred so it runs after that focus. `(pointer: coarse)`: the field is the collapsed "Enter or paste pass" button and never takes focus by itself (no on-screen keyboard); a tap opens and focuses it. The input uses `inputMode="url"`, `enterKeyHint="go"`, no autocorrect/capitalisation/spellcheck.
13. **Keys typed on the Scan tab go to the pass field** when focus is on something that does not take text (a result's button, the page). — A handheld scanner's next code is otherwise lost, or, worse, its final Enter clicks the focused "Check in" of the previous visitor. On touch screens the field opens for it (a hardware keyboard or Bluetooth scanner). Space is excluded (it activates buttons and never occurs in a pass), as are shortcuts and IME composition. Nothing happens while a dialog is open.

## Result panel

14. **One primary action.** — READY: "Check in" (solid primary, `xl`, after the facts, the panel's last row). ALREADY_CHECKED_IN: "Check out" in the outlined style beside the visitor's name, a different style and place on every screen size. If the check-in was less than 5 minutes ago there is no primary action: "Check out…" is a secondary button that opens a confirmation whose Cancel has focus, and focus goes to "Scan next". *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-19, FX-20.)* *(Amended in [phase-5-7-frontend-round2.md](phase-5-7-frontend-round2.md) FY-1.)*
15. **Enter triggers the primary action** in three ways: focus moves to it when the result appears; Enter in the empty pass field; Enter while nothing has focus. Escape (no dialog open) is "Scan next".
16. **Focus is only moved from nowhere or from inside the scanner.** — A camera result never takes focus from the visitor search or a dialog. After an action focus returns to the pass field (touch screens: to the "Enter or paste pass" button, or the field if it is open).
17. **Refused passes** show the server's message under a title, the next step where the message does not say it (completed: "register a new walk-in"; cancelled: "check with the host, then register a walk-in"; expired/not yet valid today: "check in anyway with a reason"), the visit's facts with the pass window, and the server's `check_in_options`: "Verify ID & check in" (MANUAL, one tap: the scanned pass identifies the visit) and "Check in anyway…" (OVERRIDE dialog, reason 1–300 characters, server field errors on the reason). When no check-in is possible, "Register walk-in" opens the Walk-in tab pre-filled with the visitor (loaded through `GET /visitors/{id}`), the purpose and the host (not for HOST_INACTIVE), and the reason LATE_ARRIVAL / EARLY_ARRIVAL for an expired / not-yet-valid pass of another day. An invalid pass offers an empty walk-in. A scan without a verdict (network, 429, 5xx) offers "Check again"; an action refused meanwhile (e.g. 409 VISIT_ALREADY_CHECKED_IN) shows the server message and "Check pass again", and refreshes the lists. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-24.)*
18. **Success.** — A large green check, "Checked in"/"Checked out" and the name for 1.5 s, then scanning resumes without a tap. Beep (Web Audio, 880 Hz, 120 ms) and vibration (60 ms) are one switch, "Beep on check-in and check-out", off by default and remembered on the device; the audio context is created or resumed on the user's click (browser autoplay rule), so the beep can play when the server answers.
19. **Announcements.** — The panel's polite live region says one sentence per state ("Ready to check in <name>. Verify ID.", the server message of a refusal, "<name> checked in."). A recent check-in reads "was checked in less than 5 minutes ago" rather than a duration, so the region does not speak again every minute. The camera's "scanning / paused" label is not a live region (it changes with every scan and would talk over the result); camera errors and the 8 s hint are announced through one always-mounted region.

## Lists, search and polling

20. **Polling (§10, §7.2).** — `GET /reception/today` is polled every 15 s while the screen is open; `GET /reception/inside` while the Inside tab is open (TanStack pauses both in a hidden tab). Every fetch after a list's first answer (data or error) carries `X-Background-Refresh: 1`: the poll, a refresh after a mutation, a window-focus refetch. The first load is the user's own request and counts as activity. After every check-in, check-out, bulk check-out or walk-in: `reception.*`, visit lists, visitor searches and both dashboards are invalidated and the visit detail is set from the response; a 409/404/403/410 refreshes the reception lists and searches. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-4.)*
21. **Expected tab.** — `today.expected` (capped at 200 by the server; a note says so when `counts.expected` is larger) and `today.no_show` in their own section ("Their pass has expired. A visitor who arrives late today can still be checked in anyway"), filtered inline by visitor, company, host, department and purpose (case- and accent-insensitive, client-side). The check-in is MANUAL inside the pass window and OVERRIDE outside it, judged against the current time because the list may be 15 s old; `permissions.can_check_in` decides whether there is one at all. A same-day visit the server will not check in (its host is inactive) offers "Register walk-in". Each row states where the visitor stands: "Pass valid from 08:00", "Due 09:00", "Expected now", "Late · pass valid until 11:00", "Pass expired 11:00", "No-show · …". *(Amended in [phase-5-7-frontend-round2.md](phase-5-7-frontend-round2.md) FY-3.)*
22. **A check-in from a list asks for confirmation** ("Verify ID and check in" with the name large and the "Verify ID" cue). — Unlike a scan, nothing but the receptionist's tap identifies the visit, and a check-in cannot be undone (a wrong one leaves a wrong person "inside" on the evacuation list). One extra tap is the cost.
23. **Inside tab.** — `GET /reception/inside` (any date), check-in time (with its date when not today) and time inside, host and phone, "From a previous day" (stale) and "Overdue · due out 10:00" badges. "Check out" (MANUAL) asks for confirmation (focus on Cancel if the check-in was less than 5 minutes ago). "Correct check-out time" (CORRECTED) defaults to the scheduled end, clamped between the check-in and now, on a 5-minute grid in the company time zone, with a required note; the client checks "not before the check-in, not in the future". The bulk "Check out remaining from previous days" appears when a stale visit the server lets reception check out is listed; its dialog states the count and the server's rule (scheduled end, or the check-in if later) and requires a reason. Its toast reports the server's `checked_out` count. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-7, FX-16.)* *(Amended in [phase-5-7-frontend-round2.md](phase-5-7-frontend-round2.md) FY-12.)*
24. **Find a visitor** (above the tabs). — `GET /visitors?q` (≥ 2 characters, 300 ms debounce, 10 results) with each visitor's `today_visits` (B24-11: SCHEDULED today and CHECKED_IN any day) and one action per visit: Check in (MANUAL with confirmation, or OVERRIDE outside the window) or Check out (with confirmation). A visitor without a visit today, or no match at all, offers "Register walk-in" (pre-filled with that visitor). *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-14.)* *(Amended in [phase-5-7-frontend-round2.md](phase-5-7-frontend-round2.md) FY-3, FY-4.)*

## Walk-in

25. **The walk-in being entered belongs to the screen**, so a quick scan in between does not lose it; it is reset after a successful walk-in or "Clear form". Success shows a toast and returns to the Scan tab.
26. **Fields** (lookup first, ≤ 4 inputs for a returning visitor: visitor, host, purpose, reason). — The visitor typeahead and the host picker are the invite form's (`features/visits/pickers`); the selected host's phone is a tap-to-call link under the field. The department follows the host by the invite form's rule (`walkInDepartmentChoice` mirrors `inviteDepartmentChoice`, F2-34): "No department" only for a host without an active department, and the host's own department is left out of the body so the server applies its default (assumed to match B24-23 for walk-ins). Expected end: `DateTimeField` in the company time zone, default now + 1 h, client check "after now, at most 24 hours" (D-14). Reason: the six §8.1 reasons as a touch-sized segmented quick-pick. "Reason details" appears only for OTHER, is required there, and `reason_note` is sent only for OTHER. Server field paths (`visitor.*`, `host_id`, `department_id`, `purpose`, `expected_end`, `reason`, `reason_note`) go to their fields; other errors (e.g. 409 VISITOR_ALREADY_INSIDE, WALK_INS_DISABLED) to the form alert. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-6, FX-24.)* *(Amended in [phase-5-7-frontend-round2.md](phase-5-7-frontend-round2.md) FY-5.)*
27. **`allow_walk_ins`** is read from `GET /company/settings` when the Walk-in tab opens (not on arrival at the screen). Off: "Walk-in registration is turned off". Settings that cannot be loaded do not block the form; the server refuses with WALK_INS_DISABLED if needed. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-4.)*

## Layout and accessibility

28. **Layout.** — Scan tab: camera and pass field beside the result panel from `md` (tablet portrait 820 px: the result and its "Check in" fit without scrolling), stacked on phones, where the preview shrinks to a strip while a result is shown so the result fits. Tabs are touch-sized (`xl`), two per row on phones (`phoneLayout="grid"`), badges show the expected and inside counts. Lists are cards with touch-sized buttons; their details are separate lines, so a wrap never leaves a dangling "·". The phone link keeps a 44 px tap area on touch screens without changing the line height (padding offset by negative margin). The camera box is at least 4:3 and grows with a long error message (a 4:3 spacer and the message share one grid cell) instead of cutting it off in the tablet's narrow column. The camera preview uses raw slate/white colours: it is a dark video surface, not a themed one. *(Amended in [phase-5-7-frontend.md](phase-5-7-frontend.md) FX-15.)*
29. **The page is thin** (`ReceptionPage` sets the header and starts the decoder preload; `ReceptionScreen` composes). Business rules are pure modules (`scanFlow`, `scanOutcome`, `visitActions`, `checkOutForms`, `walkInForm`, `focusRules`, `scanAnnouncement`) or hooks (`useScanStation`, `useScannerKeyboard`, `queries`); components only render and wire them.

## Known limits

- Verified with Chrome's fake camera and mocked APIs, not on a physical tablet camera, iPadOS Safari or against the running backend (which was built at the same time). The real camera path end to end is Phase 9's Y4M spec.
- A keyboard-wedge scanner on a touch tablet without a hardware keyboard needs the field opened once ("Enter or paste pass"); keys typed while it is closed open it (FR5-13), but the very first key may be lost on platforms that do not move typed text to a field focused during `keydown`.
