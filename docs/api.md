# API reference

The HTTP API of Mawdoo3 Visitors («زوار موضوع»), the visitor-pass system; its OpenAPI title is "Mawdoo3
Visitors API". Every endpoint in this document is registered in the application: 78 operations on 61
paths, re-counted from the application's OpenAPI document on 2026-10-13. Phase 12 added a company's own
identity ([`phase-12-backend.md`](decisions/phase-12-backend.md)): the platform owner's brand endpoints (5
operations) and its editing of a company's e-mail texts (7), and the public identity endpoints
(`/api/v1/public`, 3 operations, the only ones without `no-store`); `Me` and `PlatformCompany` gained the
company's `brand`. Its UX review of 2026-10-14 (B12-21 … B12-25 there) added no endpoint: `BrandPalette`
has three more roles (`surface`, `on_surface`, `surface_hover`: a company's own colour on its surfaces,
[§10.12](#1012-a-companys-identity)), a manifest's `short_name` is short and its `theme_color` is the
surface ([§10.13](#1013-public-identity-endpoints)), and some e-mail texts changed (marked "UX review"
below). Phase 11 added the platform
owner's API (`/api/v1/platform`, 15 operations) and a company's e-mail texts (`/api/v1/email-templates`, 7
operations), [`phase-11-backend.md`](decisions/phase-11-backend.md); its security and UX review of
2026-10-13 (B11-34 … B11-50 there) added no endpoint and changed what some answer (marked "review" below).
Phase 10 added
`PATCH /api/v1/auth/preferences` (B10-1 to B10-4), the language fields of `Me` and `CompanySettings`, and
the per-field error codes of a 422 (B10-18; [`phase-10-backend.md`](decisions/phase-10-backend.md)). For
the design behind it see [`docs/architecture.md`](architecture.md); for the security controls see
[`docs/security.md`](security.md); for the binding contract see
[`docs/initial-assessment.md`](initial-assessment.md) §8 (revision 5) and the decision files in
[`docs/decisions/`](decisions/).

## 1. Conventions

| Topic | Rule |
|---|---|
| IDs | UUID strings. A path ID that is not a valid UUID answers **404 `NOT_FOUND`** (not 422), like an unknown ID. |
| Paths | No trailing slash: `/api/v1/visits/` answers 404 (there are no redirects). |
| Instants in requests | ISO-8601 **with a time zone offset**, e.g. `2026-10-07T09:00:00+03:00` or `...Z`. A naive value answers 422 with "Include a time zone, e.g. 2026-10-05T09:00:00+03:00.". Accepted range 1900-01-01 … 9998-12-31 (UTC date). |
| Instants in responses | Always UTC with a `Z` suffix, e.g. `2026-10-06T11:58:13.294593Z`. |
| Dates | Date-only parameters (`date_from`, `date_to`) are `YYYY-MM-DD` in the **company's** time zone (`CompanySettings.timezone`), inclusive. |
| Unknown fields | Request bodies and query strings reject unknown keys: 422 with "This field is not allowed." for that key. |
| Text | Free text is trimmed of white space and invisible characters (zero-width space, BOM, bidirectional controls, Hangul fillers, …) at both ends; a required field that shows nothing answers "This field is required.". C0 control characters (except tab, LF, CR) and DEL are rejected. Names are single-line and may not contain bidirectional embeddings or overrides. Optional fields that are blank become `null`. |
| E-mail addresses | Stored lowercase. New addresses are validated (special-use `.local` and `.test` domains are accepted). |
| PATCH | Omitted fields are unchanged. Fields documented as "nullable" accept `null` to clear them; the others may be omitted but not `null` ("This field cannot be null."). |
| Multi-value filters | Comma-separated (`status=SCHEDULED,CHECKED_IN`) or repeated (`status=SCHEDULED&status=CHECKED_IN`); duplicates and blank items are ignored; an unknown value answers "Choose one of: …". |
| Search (`q`) | At most 100 characters; trimmed; empty means no filter; a substring match. Visitor search and visit search (`GET /visitors`, `GET /visits`) ignore case, accents and Arabic letter variants, and a query with 6 or more digits also matches phone numbers by their last 9 digits. User and host searches (`GET /users`, `GET /users/hosts`) are case-insensitive substring matches on the name (and, for `GET /users`, the e-mail address). |
| Body size | At most `MAX_REQUEST_BODY_BYTES` (default 65,536 bytes): larger bodies answer 413 `PAYLOAD_TOO_LARGE`. One request has a limit of its own, whatever that setting is: the upload of a brand image, 524,288 bytes (`PUT /platform/companies/{id}/brand/assets/{kind}`). That body also has a time: all of it within 30 seconds, else 408. |
| Caching | Every API response carries `Cache-Control: no-store`, except the successful answers of the three public identity endpoints, which say themselves how long they may be kept ([§10.13](#1013-public-identity-endpoints)). Their errors are `no-store` like everything else. |
| Links | A visitor's pass link is `{QR_BASE_URL}/pass?c={slug}#{token}`, a reset link `{APP_BASE_URL}/reset-password?c={slug}#token={token}`: the company's slug in the query, every token in the fragment, which a browser never sends. Pass links without a query (every link sent before Phase 12) are still accepted wherever a pass link is read. |

## 2. Authentication and sessions

`POST /api/v1/auth/login` with `{"email", "password"}` returns the `Me` payload and sets three cookies.
Clients send the cookies back on every request and echo the CSRF cookie in the `X-CSRF-Token` header on
unsafe methods ([§3](#3-csrf-and-origin-rules-with-examples)).

| Cookie (`COOKIE_SECURE=true`, production) | Development name (`COOKIE_SECURE=false`) | Attributes | Purpose |
|---|---|---|---|
| `__Host-vms_session` | `vms_session` | HttpOnly, Secure, SameSite=Lax, Path=/, Max-Age = `SESSION_MAX_AGE_HOURS` × 3600 | Opaque session token (the server stores only its SHA-256). |
| `__Host-vms_csrf` | `vms_csrf` | **readable by scripts**, Secure, SameSite=Strict, Path=/, same Max-Age | Value to send as `X-CSRF-Token`. |
| `__Host-vms_device` | `vms_device` | HttpOnly, Secure, SameSite=Strict, Path=/, 90 days, kept across sign-out | Marks a browser that signed in successfully (device trust: it is not blocked by the account lockout that failed attempts from elsewhere trigger). |

`COOKIE_SECURE=false` is refused in production; the `__Host-` cookies require HTTPS.

| Session rule | Value |
|---|---|
| Absolute lifetime | `SESSION_MAX_AGE_HOURS` (default 12) |
| Idle timeout | `SESSION_IDLE_MINUTES` (default 240). `last_seen_at` is refreshed at most once a minute, and **never** for requests carrying `X-Background-Refresh: 1` (send this header on automatic polling so an unattended device still times out). |
| Sign-out | `POST /auth/logout` revokes the current session and clears the session and CSRF cookies. |
| Password change | `POST /auth/change-password` revokes **every** session of the account, including the caller's, and returns a new session and CSRF cookie on the 204. |
| Password reset, deactivation | Revoke every session of the account. |
| Forced password change | While `Me.user.must_change_password` is true (admin-issued temporary password), every endpoint answers 403 `PASSWORD_CHANGE_REQUIRED` except `GET /auth/me`, `POST /auth/change-password`, `POST /auth/logout` and `PATCH /auth/preferences` (the language can be switched on the forced-change screen). |
| Language | `Me.user.preferred_language` (`ar`, `en` or null) is the user's own choice (`PATCH /auth/preferences`); null follows `Me.company.default_language`. The web application shows that language; before sign-in it uses the browser's stored choice, else the browser language, else Arabic, and a language chosen on the sign-in page is saved at sign-in to an account without a preference. The same language leads the e-mails sent to the user. Error responses keep their English `message`: clients translate by `code`, and a 422's field errors by `details.field_codes` ([§4.4](#44-field-codes-of-a-422)). |
| Expired or revoked session | 401 `NOT_AUTHENTICATED`. |

There are no API keys, bearer tokens or service accounts: every call acts as a signed-in user or as the
signed-in platform owner.

### 2.1 The platform owner's session

The platform owner (Phase 11, B11-1 … B11-8) is not a user of any company. It signs in with
`POST /api/v1/platform/auth/login` and receives cookies of its own, so a browser can hold a company session
and a platform session side by side; neither is ever accepted by the other's endpoints (401).

| Cookie (`COOKIE_SECURE=true`) | Development name | Attributes | Purpose |
|---|---|---|---|
| `__Host-vms_platform_session` | `vms_platform_session` | HttpOnly, Secure, SameSite=Lax, Path=/, Max-Age = `PLATFORM_SESSION_MAX_AGE_HOURS` × 3600 | Platform session token |
| `__Host-vms_platform_csrf` | `vms_platform_csrf` | **readable by scripts**, Secure, SameSite=Strict, Path=/, same Max-Age | Value to send as `X-CSRF-Token` on unsafe `/platform` requests |
| `__Host-vms_platform_device` | `vms_platform_device` | HttpOnly, Secure, SameSite=Strict, Path=/, 90 days | Device trust for platform accounts |

| Rule | Value |
|---|---|
| Absolute lifetime | `PLATFORM_SESSION_MAX_AGE_HOURS` (default 8; production at most 12) |
| Idle timeout | `PLATFORM_SESSION_IDLE_MINUTES` (default 30; production at most 60). As for a company session, `last_seen_at` is refreshed at most once a minute and **never** for a request carrying `X-Background-Refresh: 1` (B11-34): send the header on the session heartbeat and on every refetch nobody asked for, and never on a request of the person, or an open tab would not time out |
| Who is signed in | `GET /api/v1/platform/auth/me` → `PlatformMe`, or 401 |
| Forced password change | While `PlatformMe.admin.must_change_password` is true, every platform endpoint answers 403 `PASSWORD_CHANGE_REQUIRED` except `GET /platform/auth/me`, `POST /platform/auth/logout`, `POST /platform/auth/change-password` and `PATCH /platform/auth/preferences` |
| Password change | Revokes every platform session, the caller's included, and returns new platform cookies on the 204 |
| Accounts | Created and reset only by `python -m app.cli create-platform-admin`; there is no forgot-password for platform accounts. The temporary password the command generates signs in even while failed sign-ins keep the account locked (B11-35) |
| A write in flight | A platform write whose session ends while it waits (a sign-out in another tab, the operator's reset) answers 401 `NOT_AUTHENTICATED` and writes nothing (B11-38) |

## 3. CSRF and Origin rules, with examples

For every `POST`, `PUT`, `PATCH` and `DELETE` under `/api/v1` a global middleware applies, in order:

1. `Sec-Fetch-Site: cross-site` is refused; `Sec-Fetch-Site: same-site` is refused unless `Origin` is in `ALLOWED_ORIGINS`.
2. If an `Origin` header is present, it must be in `ALLOWED_ORIGINS`.
3. If the request carries a session cookie that belongs to a live session, `X-CSRF-Token` must equal that session's CSRF token.

Rule 3 is skipped only for `POST /auth/login`, `POST /auth/forgot-password` and
`POST /auth/reset-password` (they create or recover a session); rules 1 and 2 still apply to them.
Requests under `/api/v1/platform` follow the same rules with the **platform** session cookie and its
CSRF cookie (`__Host-vms_platform_csrf`, sent as `X-CSRF-Token`); only `POST /platform/auth/login` skips
rule 3, and a company session's token never passes for a platform request (or the reverse). A
failure answers **403 `CSRF_FAILED`** and is audited. Non-browser clients that send neither `Origin`
nor `Sec-Fetch-Site` pass rules 1 and 2 and only need the token.

### 3.1 curl (Linux, macOS, Git Bash on Windows)

Verified against a development server (`COOKIE_SECURE=false`, hence the cookie name `vms_csrf`). Against
a production deployment use its `https://` origin and the cookie name `__Host-vms_csrf`.

```bash
BASE=http://127.0.0.1:8000            # production: https://vms.example.com
JAR=$(mktemp)
CSRF_COOKIE=vms_csrf                  # production: __Host-vms_csrf

# 1. Sign in: stores the session, CSRF and device cookies in the jar, prints the Me payload.
curl -sS -c "$JAR" -H 'Content-Type: application/json' \
  -d '{"email":"admin@demo.local","password":"Demo-Visitor-2026"}' \
  "$BASE/api/v1/auth/login"

# 2. Read the CSRF token from the jar (Netscape format: column 6 = name, column 7 = value).
CSRF=$(awk -v n="$CSRF_COOKIE" '$6 == n {print $7}' "$JAR")

# 3. Safe methods need only the cookies.
curl -sS -b "$JAR" "$BASE/api/v1/auth/me"
curl -sS -b "$JAR" "$BASE/api/v1/visits?status=SCHEDULED,CHECKED_IN&page=1&page_size=25"

# 4. Unsafe methods also need the header.
curl -sS -b "$JAR" -H 'Content-Type: application/json' -H "X-CSRF-Token: $CSRF" \
  -d '{"name":"Facilities"}' "$BASE/api/v1/departments"

# Without the header the same request answers 403 CSRF_FAILED:
curl -sS -b "$JAR" -H 'Content-Type: application/json' \
  -d '{"name":"Facilities 2"}' "$BASE/api/v1/departments"

# 5. Sign out (clears the session and CSRF cookies).
curl -sS -b "$JAR" -c "$JAR" -X POST -H "X-CSRF-Token: $CSRF" "$BASE/api/v1/auth/logout"
```

`admin@demo.local` / `Demo-Visitor-2026` exist only in a database seeded with
`python -m app.cli seed-demo` or `seed-e2e` (both refused in production).

### 3.2 PowerShell (Windows PowerShell 5.1 and PowerShell 7)

In Windows PowerShell 5.1, `curl` is an alias of `Invoke-WebRequest`; use `Invoke-RestMethod` with a web
session (verified on Windows PowerShell 5.1), or call `curl.exe` explicitly with the commands of §3.1.

```powershell
$base = 'http://127.0.0.1:8000'          # production: https://vms.example.com
$csrfCookie = 'vms_csrf'                 # production: __Host-vms_csrf

$body = @{ email = 'admin@demo.local'; password = 'Demo-Visitor-2026' } | ConvertTo-Json
$me = Invoke-RestMethod -Method Post -Uri "$base/api/v1/auth/login" -ContentType 'application/json' `
      -Body $body -SessionVariable vms
$csrf = $vms.Cookies.GetCookies($base)[$csrfCookie].Value

Invoke-RestMethod -Uri "$base/api/v1/users/hosts?q=amal" -WebSession $vms
Invoke-RestMethod -Method Post -Uri "$base/api/v1/departments" -ContentType 'application/json' `
      -Body '{"name":"Facilities"}' -WebSession $vms -Headers @{ 'X-CSRF-Token' = $csrf }

# Error envelopes: the body is in ErrorDetails, the status in the exception's response.
try { Invoke-RestMethod -Uri "$base/api/v1/visits/00000000-0000-0000-0000-000000000000" -WebSession $vms }
catch { $_.Exception.Response.StatusCode.value__; $_.ErrorDetails.Message }   # 404 NOT_FOUND envelope

Invoke-RestMethod -Method Post -Uri "$base/api/v1/auth/logout" -WebSession $vms `
      -Headers @{ 'X-CSRF-Token' = $csrf } | Out-Null
```

### 3.3 Notes for direct calls

- **Client address.** The API takes the client address from `X-Forwarded-For` only when the direct peer
  is listed in `TRUSTED_PROXIES`. The development `.env` trusts loopback (the Vite proxy), so a direct
  call to `127.0.0.1:8000` without `X-Forwarded-For` has no client address: it is logged and audited with
  an empty IP, and all such callers share one per-IP rate-limit budget.
- **Change password.** After `POST /auth/change-password` the old session cookie stops working; keep the
  cookies of the 204 response (`curl -c "$JAR"`; `Invoke-RestMethod` updates the session object).

## 4. Errors

### 4.1 Envelope

Every non-2xx response has this body:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please correct the highlighted fields.",
    "details": {
      "fields": { "name": "This field is required.", "colour": "This field is not allowed." },
      "field_codes": {
        "name": { "code": "required", "params": {} },
        "colour": { "code": "not_allowed", "params": {} }
      }
    }
  },
  "request_id": "e4d90521c8114b33bb486462e00e830a"
}
```

| Member | Meaning |
|---|---|
| `error.code` | Stable machine-readable code (table below). |
| `error.message` | User-facing text in English, safe to display. Never contains a stack trace or internal data. |
| `error.details` | Object, possibly empty. Shapes: `fields` (422: `{path: message}` with the request's own field names, e.g. `visitor.email`, `reason`, `body` for whole-body problems) and, for exactly the same paths, `field_codes` (422: `{path: {code, params}}`, [§4.4](#44-field-codes-of-a-422)); `field` (409 `CONFLICT`); `visitor_id` (409 `VISITOR_EXISTS`, only for callers who read every visitor); `visit` and `check_in_options` (scan and check-in refusals, see [§10.8](#108-reception)); `database: "unavailable"` (503 from `GET /health`). |
| `request_id` | The same value as the `X-Request-ID` response header; it is in the server logs and audit rows. Quote it when reporting a problem. |

429 responses carry a `Retry-After` header (seconds). 503 responses from nginx (API down) carry
`Retry-After: 5`.

### 4.4 Field codes of a 422

Since Phase 10 (`docs/decisions/phase-10-backend.md`, B10-18) every entry of `details.fields` has a twin in
`details.field_codes` under the same path: a stable machine code and its parameters, so a client can show
the problem in its own language instead of matching the English message. The messages are unchanged; the
codes are additive.

```json
"field_codes": {
  "purpose":   { "code": "too_long", "params": { "max": 500 } },
  "language":  { "code": "invalid_choice", "params": { "choices": ["ar", "en"] } },
  "date_from": { "code": "date_out_of_range", "params": { "max": "9998-12-31", "min": "1900-01-01" } }
}
```

- Each entry is `{"code": <one of the codes below>, "params": {...}}`. `params` is always present and holds

## 5. Pagination

Paginated endpoints take `page` (1 … 100,000, default 1) and `page_size` (1 … 100, default 25) and
return:

```json
{ "items": [ ... ], "page": 1, "page_size": 25, "total": 33 }
```

`total` is the exact number of matching items in the caller's scope. Every list has a stable order with
a unique tie-breaker, so pages never overlap or skip items while data is unchanged:

| Endpoint | Order |
|---|---|
| `GET /users` | `lower(full_name)`, `id` |
| `GET /visitors` | folded name (case, accents and Arabic letter variants ignored), `id` |
| `GET /visitors/{visitor_id}/visits` | `scheduled_start` descending, `id` descending |
| `GET /visits` | `scheduled_start`, then `id`, both in the direction of `order` (`asc` or `desc`, default `desc`) |
| `GET /audit-logs` | `seq` descending (newest first) |

A page past the end returns `items: []` with the correct `total`. Non-paginated lists: `GET /users/hosts`
(at most 50), `GET /departments`, `GET /reception/today` (each list at most 200 items; counts are exact),
`GET /reception/inside` (never capped).

The platform owner holds no role: its endpoints (`/api/v1/platform`) need a platform session and accept

## 7. Rate limits

Limits are sliding windows held in the memory of the API process that answers. The deployment runs
one main process, which receives every sign-in and every write and counts every policy below; the
Compose layout adds three read processes for six GET endpoints (`/reception/today`,
`/reception/inside`, `/reports/summary`, `/audit-logs`, `/dashboard/admin` and `GET /visits`), which
consult only `api_per_user` and count it for their own requests (`deploy/README.md` §4). Defaults are
set by environment variables (see `.env.example`); production refuses `RATE_LIMIT_ENABLED=false` and
the guessing limits above ten times their defaults. A refused request answers 429 with `Retry-After` and is
audited as `RATE_LIMITED` with the policy name in `metadata.policy`.

"IP" means the client address (IPv4 address, or the IPv6 /64); "/48" is the client's IPv6 /48 prefix
(not applied to IPv4 clients).

account, typed e-mail and device, and **shares** `login_failures_ip` and `login_failures_prefix` with the
companies' sign-in; `POST /platform/auth/change-password` takes `password_change_failures` and
`password_changes_per_user`; `api_per_user` is counted per platform account. A reset link sent by the
platform owner (`POST /platform/companies/{id}/admins/{user_id}/password-reset`) spends the account's
`forgot_password_account` budget and answers 429 beyond it. Platform refusals are audited in the platform's
trail. Since the review (B11-35, B11-42, B11-43):

- the platform account's `login_failures_account` and `password_change_failures` budgets are counted per
  account **and password** (they start afresh when the password is reset or changed), and a sign-in with
  the temporary password that `create-platform-admin` generated is judged by a `login_failures_device`
  budget of that password instead of the account's;
- the password change that completes an operator-issued temporary password takes no slot of
  `password_changes_per_user`;
- `user_email_refusals_per_user` also bounds the platform owner: 10 an hour per platform account for
  `POST /platform/companies` and `POST /platform/companies/{id}/admins` refused with
  `USER_EMAIL_UNAVAILABLE`, then 429 for every such creation;
- each administrator receives at most 5 notices of platform actions an hour (the numbers of
  `password_notices_per_user`); beyond that the action is done and the e-mail left out.

The public identity endpoints answer whether a slug names an active company, to anyone; their two budgets
are therefore among the guessing limits production holds to ten times their default. They are counted by
the main process, before anything is looked up, and are apart from every sign-in budget (Phase 12, B12-9).

A sign-in refused with `COMPANY_INACTIVE` (valid credentials, deactivated company) is not a failure: it
counts towards no `login_failures_*` budget and takes a slot of `login_successes_account` instead (B11-46).

Concurrent attempts cannot exceed a failure limit: slots are reserved atomically before the work (for
login, before the Argon2 verification). Because the counters live in memory, a restart resets them.

"Required" fields must be present; `?` marks optional fields. Lengths are in characters after trimming.

**`LoginRequest`** — `email` (string, 1–320; normalised, not validated), `password` (string, 1–1024).

**`ChangePasswordRequest`** — `current_password` (1–1024), `new_password` (1–1024; policy below).

**`ForgotPasswordRequest`** — `email` (1–320).

**`ResetPasswordRequest`** — `token` (1–256; the value after `#token=` in the reset link), `new_password`.

**`PreferencesUpdate`** — `language` (`Language`, required: `ar` or `en`; anything else, null included,

Password policy (new, reset and temporary passwords): 12–128 characters; not the account's e-mail
address; not on the embedded list of common passwords; not a common word, or the account's name,
e-mail or company, with only digits and symbols added; a changed password must differ from the
current one. Violations answer 422 on the password field with the reason.

**`UserCreate`** — `full_name` (1–200, one line), `email` (≤ 320, valid address), `phone?` (≤ 40, digits,

`department_id?` (UUID of an active department of the company; nullable), `temporary_password` (password
policy; expires after 72 hours; the user must change it at first sign-in).

**`UserUpdate`** — all optional: `full_name` (not null), `phone` (nullable), `department_id` (nullable),

(not null).

**`CompanySettingsUpdate`** — all optional: `name` (1–200, one line, not null; the English or only
name), `name_ar` (the Arabic name: the rules of `name`, i.e. trimmed, 1–200 characters, one line, no
control or text-direction characters; null or blank clears it), `default_language` (`Language`, not
null), `timezone` (IANA name known to both Python and PostgreSQL, not null), `address` (≤ 1000,
nullable; the English or only address), `address_ar` (the address in Arabic: the rules of `address`;
nullable), `email_domain` (≤ 255, a domain name, nullable), `pass_grace_before_minutes` / `pass_grace_after_minutes` (0–1440, not null; apply to
visits created or rescheduled afterwards), `notify_host_on_check_in`, `allow_walk_ins` (booleans, not
null).

**`VisitorCreate`** — `full_name` (1–200), `email?` (nullable; unique per company), `phone?` (nullable),
`company_name?` (≤ 200, nullable).
**`VisitorUpdate`** — all optional: `full_name` (not null), `email` (nullable: clearing it revokes the
passes of the visitor's SCHEDULED visits; changing it revokes them and e-mails a new invitation with a
new pass to the new address for each), `phone` (nullable), `company_name` (nullable).

**`VisitorInput`** (inline new visitor inside `VisitCreate` and `WalkInCreate`) — same fields as
`VisitorCreate`. If the e-mail matches an existing visitor of the company, that visitor is reused (only
if the names match after folding; otherwise 409 `VISITOR_EXISTS`).

**`VisitCreate`** — exactly one of `visitor_id` (UUID of a visitor the caller may read) or `visitor`
(`VisitorInput`); `host_id` (the caller's own ID; an administrator may name any active user holding
EMPLOYEE or SYSTEM_ADMIN, anyone else gets 422 `host_must_be_self`); `department_id?` (active
department; default: the host's department if it is active); `purpose` (1–500); `scheduled_start`,
`scheduled_end` (instants with offset; end after start, at most 24 h long, start not more than 5 min in
the past and at most 365 days ahead); `send_invitation` (boolean, required; `true` needs a visitor
e-mail).

**`VisitUpdate`** — all optional: `purpose` (not null), `department_id` (nullable),
`scheduled_start`, `scheduled_end` (not null; the start rules apply only when the start changes).

**`VisitCancel`** (`VisitCancelRequest`) — the whole body is optional. `reason?` (≤ 300, nullable),
`notify_visitor?` (default `true`; a visitor is e-mailed only if an invitation was requested for the
visit; ignored when `Visit.visitor_calendar_sent` is true: the visitor is then always e-mailed, so that
the event leaves the visitor's calendar, B14-16, and that e-mail carries no `reason` when
`notify_visitor` is false, B14-32).

**`CheckInRequest`** — discriminated by `method`:
`{"method":"QR","pass_token":"<scanner input, ≤ 4096>"}` |
`{"method":"MANUAL"}` |
`{"method":"OVERRIDE","reason":"<1–300>"}`. The name is the contract snapshot's; the OpenAPI document has
no component of that name but a `oneOf` of `QrCheckIn`, `ManualCheckIn` and `OverrideCheckIn`.

**`CheckOutRequest`** — discriminated by `method`:
`{"method":"QR","pass_token":"..."}` |
`{"method":"MANUAL"}` |
`{"method":"CORRECTED","check_out_at":"<instant between the check-in and now>","note":"<1–300>"}`. In the
OpenAPI document: a `oneOf` of `QrCheckOut`, `ManualCheckOut` and `CorrectedCheckOut`.

**`ScanRequest`** — `token` (≤ 4096): the raw scanner or paste input (a pass URL or a bare token). It is
not trimmed or validated by the schema; anything that is not a pass of the caller's company answers
404 `PASS_INVALID`.

**`StaleCheckOutRequest`** (`CheckOutStaleRequest`) — `reason` (1–300; stored as the check-out note).

**`WalkInCreate`** — exactly one of `visitor_id` or `visitor` (`VisitorInput`); `host_id`;
`department_id?`; `purpose` (1–500); `expected_end` (instant after now, at most 24 h ahead); `reason`
(enumeration above); `reason_note?` (≤ 300; required when `reason` is `OTHER`; stored as the check-in
note). `LOST_PASS` must name a registered visitor (`visitor_id`, or inline details whose e-mail matches
a registered visitor); new visitor details are refused with 422 on `reason`. It is also refused with
422 on `reason` while that visitor has a SCHEDULED visit whose pass window opens before the end of the
company-local day: the message points reception to that visit (check them in there instead, after an
ID check), so the reported-lost pass stops working at check-out.

## 10. Endpoint reference

Each entry lists only what is specific to the endpoint; [§4.3](#43-errors-common-to-all-endpoints)
lists the errors every endpoint can return.

### 10.1 Health

#### `GET /api/v1/health` — public

Liveness and database reachability. Answers within 3 s; the database result is cached for 1 s.

- **200** `{"status":"ok","database":"ok"}`
- **503** `SERVICE_BUSY` with `details.database = "unavailable"`

### 10.2 Authentication

#### `POST /api/v1/auth/login` — public, CSRF-token exempt

Body `LoginRequest`. On success: 200 `Me`, cookies set ([§2](#2-authentication-and-sessions)); a still
valid session cookie of the same browser is revoked first. Every failure answers the same 401, whether
the account exists or not, with one exception that only valid credentials reach (the 409 below).

- **401** `INVALID_CREDENTIALS`
- **409** `COMPANY_INACTIVE` "This company is deactivated." (review, B11-46): the e-mail and the password
  are right, the account is active and its password current, and the platform owner deactivated the
  company. No session, no cookie. A wrong password or an unknown address still gets the 401, after the
  same single password verification, so nobody without the password learns that a company is deactivated
  or that an address has an account. It is not a failed attempt (it counts towards no lockout); it takes
  a slot of `login_successes_account` instead.
- **429** `RATE_LIMITED` (`login_failures_*`, `login_successes_account`)
- **503** `SERVICE_BUSY` (password hashing at capacity)
- Audit: `AUTH_LOGIN_SUCCEEDED`; `AUTH_LOGIN_FAILED` with `metadata.reason` (`unknown_account`, `bad_password`, `inactive`, `password_expired`, `company_inactive`, `credentials_changed`, and in production `seed_account`: a demo account of `seed-demo` / `seed-e2e`, B11-36); `AUTH_ACCOUNT_THROTTLED` when a failure starts a lockout; `RATE_LIMITED` for refused attempts.

#### `POST /api/v1/auth/logout` — session

Revokes the current session; clears the session and CSRF cookies (the device cookie is kept). **204**.

#### `GET /api/v1/auth/me` — session

**200** `Me`. Allowed while a password change is required, so the client can tell. Since Phase 12
`Me.company` carries the company's `slug` and its `brand` (`CompanyBrand`, [§10.12](#1012-a-companys-identity)):
the identity the application shows from the first answer after sign-in. Since Phase 14 also its `address`
and `address_ar` (show `address_ar` in Arabic when it is set, else `address`, and the other way round), the
location of the calendar events the application offers (phase-14-backend.md B14-13).

#### `POST /api/v1/auth/change-password` — session

Body `ChangePasswordRequest`. **204** with a new session cookie, CSRF cookie and device cookie; every
other session of the account and the caller's previous session are revoked; a "password changed" e-mail
is sent to the account (budgeted).

- **400** `INVALID_CURRENT_PASSWORD`
- **401** `NOT_AUTHENTICATED` (the session ended while the request ran)
- **422** on `new_password` (policy, or equal to the current password)
- **429** `RATE_LIMITED` (`password_change_failures`, `password_changes_per_user`)
- **503** `SERVICE_BUSY`

#### `PATCH /api/v1/auth/preferences` — session

Body `PreferencesUpdate`. **200** `Me` with `user.preferred_language` set. The caller's own interface and
e-mail language: the web application switches to it, and the e-mails sent to the user (host arrival,
password reset and change) lead with it. Allowed while a password change is required (the forced-change
screen offers the switch). The usual session, CSRF and Origin rules apply; it spends only the per-user
API budget. Choosing the current language again writes nothing. Not audited: a display preference
changes no access and no data, and an append-only row per switch would let one session add hundreds of
rows a minute ([`phase-10-backend.md`](decisions/phase-10-backend.md) B10-4).

- **422** `VALIDATION_ERROR` on `language` (anything but `ar` or `en`)

#### `POST /api/v1/auth/forgot-password` — public, CSRF-token exempt

Body `ForgotPasswordRequest`. Always **202** `{"message": "If an account exists for that email
address, we have sent instructions to reset the password."}`, whether or not the address has an account
and whether or not a limit dropped the request. For an active account, a reset e-mail with the link
`{APP_BASE_URL}/reset-password?c=<slug>#token=<token>` (valid 30 minutes; since Phase 12 it names the
account's company, whose identity the reset page shows) is sent in the background; issuing it
invalidates older unused tokens of the account.

#### `POST /api/v1/auth/reset-password` — public, CSRF-token exempt

Body `ResetPasswordRequest`. **204** and a device cookie for this browser; all sessions and unused reset
tokens of the account are revoked, the account's login lockout is lifted, and a "password changed"
e-mail is sent. A password-policy error does not use up the token.

- **400** `INVALID_RESET_TOKEN`
- **422** on `new_password`
- **429** `RATE_LIMITED` (`reset_password_ip`, `reset_password_prefix`)

### 10.3 Users

#### `GET /api/v1/users/hosts` — any signed-in user

Query (`UserListQuery`): `q?` (name or e-mail), `role?` (multi-value `Role`; users holding any of them),

#### `POST /api/v1/users` — `ADMINISTER`

Body `UserCreate`. **201** `User` with `must_change_password: true`. Audit `USER_CREATED`.

- **409** `USER_EMAIL_UNAVAILABLE` (address used by any user of any company; audited `USER_CHANGE_REFUSED`)
- **422** on `temporary_password` (policy), `department_id` (unknown, other company or inactive), …

**200** `User`; **404** for unknown or other-company IDs.

  hosts** (reason "Host is no longer available"; passes revoked; visitors e-mailed if an invitation had
  been requested); `cancelled_visits` in the response gives the number when it is at least 1.

### 10.4 Departments

#### `GET /api/v1/departments` — any signed-in user

Active departments ordered by name. `include_inactive=true` is for administrators; other roles get
**403** `FORBIDDEN`. **200** `Department[]`.

#### `POST /api/v1/departments` — `ADMINISTER`

Body `DepartmentCreate`. **201** `Department`. **409** `CONFLICT` with `details.field = "name"` when the
name exists in the company (ignoring case), or `details.field = "name_ar"` ("A department with this
Arabic name already exists.") when the Arabic name does. Audit `DEPARTMENT_CREATED`.

A department is shown by `name_ar` in an Arabic interface when it is set, and by `name` otherwise
(everywhere a `DepartmentRef` appears, and in the reports' `by_department`). So that two departments never
read the same in either interface, no value of a department may be a value of another department of the
company, across the languages too, ignoring case and inactive departments included (B10-29): a name equal
to another department's Arabic name is **409** `CONFLICT` on `name` ("A department with this Arabic name
already exists."), and an Arabic name equal to another department's name is **409** `CONFLICT` on
`name_ar` ("A department with this name already exists."). A department's own name and Arabic name may be
equal. The checks run in this order: `name` against names, then against Arabic names; `name_ar` against
Arabic names, then against names.

#### `PATCH /api/v1/departments/{department_id}` — `ADMINISTER`

Body `DepartmentUpdate`. **200** `Department`. A rename in either language updates the department-name
snapshots (`name` and `name_ar` of the visit's `department`) of SCHEDULED visits; checked-in and later
visits keep theirs. Errors: **404**, **409** `CONFLICT` on `name` or `name_ar`, as for `POST`; only a
value that changes is checked, the department's own values never conflict, and a value that changes only
in case is not compared across the languages (so departments saved before B10-29 that share a value stay
editable). Clearing `name_ar` never conflicts. Audit
`DEPARTMENT_UPDATED` with the changed field names (`name`, `name_ar`, `is_active`).

### 10.5 Company settings

#### `GET /api/v1/company/settings` — any signed-in user

**200** `CompanySettings` of the caller's company.

#### `PATCH /api/v1/company/settings` — `ADMINISTER`

Body `CompanySettingsUpdate`. **200** `CompanySettings`. **422** on `timezone` ("Choose a timezone from
the list, for example Asia/Amman."), on `name_ar` (the rules of `name`) and on `default_language`
(anything but `ar` or `en`). Changing the time zone rewrites no stored instant. `default_language` is the

visitors; `name_ar` names the company in Arabic text (the interface in Arabic, the Arabic part of every

`brand_color`, `color`, `logo_url` or `slug` answers 422 with `not_allowed` on that field and changes

### 10.6 Visitors

Visitor reads are scoped: SYSTEM_ADMIN, RECEPTIONIST and MANAGEMENT read every visitor of the company;
EMPLOYEE-only users read visitors they created or that are linked to their own visits, and see only
their own visits in a visitor's history and statistics. A visitor outside the scope answers 404.

#### `GET /api/v1/visitors` — `READ_VISITORS`

Query (`VisitorSearchQuery`): `q?`, `page`, `page_size`. Without `q`, lists every visitor in scope.
**200** `Paginated[VisitorSearchItem]` (`VisitorSearchPage`); `today_visits` holds the visitor's
SCHEDULED visits of today (plus those whose pass window opens today and has not ended) and CHECKED_IN
visits of any day, within scope.

#### `POST /api/v1/visitors` — `CREATE_VISITOR`

Body `VisitorCreate`. **201** `Visitor`. **409** `VISITOR_EXISTS` when the e-mail belongs to a visitor
of the company (`details.visitor_id` only for callers who read every visitor). Audit
`VISITOR_CREATED`.

#### `GET /api/v1/visitors/{visitor_id}` — `READ_VISITORS`

**200** `Visitor`; **404** outside the caller's scope.

#### `PATCH /api/v1/visitors/{visitor_id}` — `EDIT_VISITOR`

Body `VisitorUpdate`. **200** `Visitor`. Name and company changes update the snapshots of the visitor's
SCHEDULED visits. An e-mail change revokes the active passes of the visitor's SCHEDULED visits and sends
each a new invitation with a new pass to the new address; clearing the e-mail only revokes them. Either
way, each visit whose event the old address's calendar holds is first taken out of that calendar: a
`VISITOR_CALENDAR` message to the old address whose `CANCEL` names nothing of the visit, with
`calendar_sequence` one higher, and the new address's calendar invitation one higher still (Phase 14,
B14-17, B14-30). A REQUEST still waiting to go to the old address is closed (FAILED, B14-29). A new
address that is another spelling of the same mailbox (letter case, a `+tag`, Gmail's dots) loses nothing:
no withdrawal, and its calendar invitation updates the entry.

- **403** `FORBIDDEN` (readable but not editable by this EMPLOYEE)
- **404**
- **409** `VISITOR_EXISTS` (new e-mail belongs to another visitor)
- **422** on `email` when the re-invitations can never fit the daily invitation budget (the message
  says how many visits are affected)
- **429** `INVITATION_LIMIT`

#### `GET /api/v1/visitors/{visitor_id}/visits` — `READ_VISITORS`

Query `page`, `page_size`. **200** `Paginated[Visit]` (`VisitPage`), newest first; **404** outside scope.

NO_SHOW.

#### `GET /api/v1/visits` — `READ_VISITS`

Query (`VisitListQuery`):

| Parameter | Type | Meaning |
|---|---|---|
| `scope` | `mine` \| `all` | Default `all` for SYSTEM_ADMIN, RECEPTIONIST, MANAGEMENT; always `mine` (visits the caller hosts or created) for EMPLOYEE-only users |
| `status` | multi-value `VisitStatus` | |
| `date_from`, `date_to` | `YYYY-MM-DD` | company-local dates of `scheduled_start`, inclusive; `date_to` not before `date_from` |
| `host_id`, `visitor_id`, `department_id` | UUID | must name a user, visitor (in scope) or department of the company, otherwise 422 on that parameter |
| `needs_attention` | boolean | SCHEDULED visits whose latest invitation FAILED, or NOT_SENT although requested |
| `q` | text | matches the visit's visitor, visitor-company and host names and, within the caller's scope, the stored visitor's details and phone digits |
| `order` | `asc` \| `desc` | by `scheduled_start`; default `desc` |
| `page`, `page_size` | | [§5](#5-pagination) |

**200** `Paginated[Visit]` (`VisitPage`).

#### `POST /api/v1/visits` — `CREATE_VISIT`

Body `VisitCreate`. Creates a SCHEDULED visit and always issues a pass; queues the invitation e-mail when
`send_invitation` is true, followed by its calendar invitation (`VISITOR_CALENDAR`, the visit as an event of
the visitor's calendar, without the pass), and always the host's notice of the visit (`HOST_VISIT_SCHEDULED`,
with the host's event) (delivered after the response, in that order; the visit is kept even if delivery
fails). Phase 14, [phase-14-backend.md](decisions/phase-14-backend.md) B14-1. The calendar invitation and
the host's notice are left out beyond their budgets (`calendar_emails_per_company_day`,
`host_visit_notices_per_user_day`, B14-15).
**201** `VisitCreateResult`: `pass_url` (`{QR_BASE_URL}/pass?c=<slug>#<token>` since Phase 12) is returned **only here and
never again**; `visitor_match.reused` tells whether an existing visitor record was linked.

- **409** `VISITOR_EMAIL_REQUIRED`; `VISITOR_EXISTS` (inline e-mail registered under another name; with
  `details.visitor_id` for callers who read every visitor)
- **422** on `host_id`, `department_id`, `visitor_id`, `visitor`, `scheduled_start`, `scheduled_end`, …;
  on `host_id` with `host_must_be_self` when a caller who is not an administrator names another host
  (checked before the host is looked up, so the answer says nothing about that user)
- **429** `INVITATION_LIMIT` (`invitations_per_user_day`)
- **503** `SERVICE_BUSY` (a concurrent change kept moving the matched visitor's e-mail)
- Audit: `VISIT_CREATED` (`host_notified`, `host_notice_limited_by`), `PASS_ISSUED`, `INVITATION_QUEUED` (`calendar_sent`, `notice_limited_by`), later `INVITATION_SENT` / `INVITATION_FAILED`; `VISITOR_CREATED` for an inline new visitor.

#### `GET /api/v1/visits/{visit_id}` — `READ_VISITS`

**200** `Visit`; **404** outside the caller's scope.

#### `PATCH /api/v1/visits/{visit_id}` — `MANAGE_OWN_VISITS`

Body `VisitUpdate`. Only SCHEDULED visits. A schedule change recomputes the pass window with the
current grace settings and **keeps the pass**; the visitor is e-mailed a "rescheduled" notice only if
an invitation was requested for the visit (within the reschedule budgets), and the host (when active and
told of the visit) a `HOST_VISIT_RESCHEDULED` (within the host's e-mails' budget, not the reschedule
budgets, B14-15); each carries its calendar event at the new time. A new time raises `calendar_sequence`
by one. **200** `Visit`.

- **403** `FORBIDDEN` (readable but not owned)
- **404**
- **409** `VISIT_NOT_EDITABLE`
- **422** schedule rules, `department_id`
- Audit `VISIT_UPDATED` (changed field names), `VISIT_RESCHEDULED` (`visitor_notified`, `email_message_id`, `calendar_sent`, `notice_limited_by`: the visitor's notice; `host_notified`, `host_calendar_sent`, `host_notice_limited_by`: the host's). A notice goes without its event beyond the company's calendar events, or with calendar invitations switched off to a calendar that does not hold the visit (B14-27, B14-28).

#### `POST /api/v1/visits/{visit_id}/cancel` — `MANAGE_OWN_VISITS`

Optional body `VisitCancel`. Cancels a SCHEDULED visit, revokes its pass, and e-mails the visitor when
`notify_visitor` is true **and** an invitation was requested for the visit, and always when the visitor's
calendar was sent the visit (`visitor_calendar_sent`, B14-16); the host, when active and told of the
visit, gets `HOST_VISIT_CANCELLED` whatever `notify_visitor` says (within the host's e-mails' budget).
Both carry the cancellation of their calendar event; `calendar_sequence` is raised by one. **200**
`Visit` (see `last_notice` for the visitor's notice). Audit `VISIT_CANCELLED` (`visitor_notified`,
`host_notified`, `host_notice_limited_by`, …).

- **403**, **404**
- **409** `INVALID_STATE_TRANSITION` (not SCHEDULED)

#### `POST /api/v1/visits/{visit_id}/invitation` — `MANAGE_OWN_VISITS`

Resends the invitation: **rotates the pass** (the previous QR code stops working), closes any invitation
of the visit still PENDING, and sends a new invitation, followed by its calendar invitation (the same event,
its current version, where it may go). **200** `VisitResendResult` with the new one-time `pass_url`.

When only the calendar invitation failed (`visit.invitation.calendar_failed` true: the invitation went
out), it sends **the calendar invitation alone** again instead (Phase 14, B14-31): the same version of
the visitor's event with a new `DTSTAMP`; the pass is not rotated, no invitation is sent, and `pass_url`
is **null**. It counts as one of the visit's hourly resends, of the user's daily invitations and of the
company's calendar events, all or none, and is sent with calendar invitations switched off too (that
calendar was sent the visit). Audit `INVITATION_QUEUED` with `pass_id` null and `calendar_sent` true.

- **403**, **404**
- **409** `VISIT_NOT_EDITABLE`, `VISITOR_EMAIL_REQUIRED`
- **429** `INVITATION_LIMIT` (`invitations_per_user_day`, `invitation_resends_per_visit`; for the calendar
  invitation alone also `calendar_emails_per_company_day`)

#### `POST /api/v1/visits/{visit_id}/pass` — `MANAGE_OWN_VISITS`

Rotates the pass and returns the new link once, **without sending any e-mail** (for hosts who share the
pass themselves). **200** `VisitPassResult`.

- **403**, **404**
- **409** `VISIT_NOT_EDITABLE`
- **429** `RATE_LIMITED` (`invitation_resends_per_visit`, shared with resends)

#### `POST /api/v1/visits/{visit_id}/check-in` — `RECEPTION`

Body `CheckInRequest`. **200** `Visit` (CHECKED_IN). Methods:

| Method | Allowed when |
|---|---|
| `QR` | `pass_token` is a pass of **this** visit and the scan evaluation is READY (row 9 of [§10.8](#108-reception)) |
| `MANUAL` | reception verified the visitor's ID; visit SCHEDULED, inside the pass window, host available (a replaced pass does not prevent it) |
| `OVERRIDE` | `reason` given; visit SCHEDULED or NO_SHOW, on the visit's company-local day (any time of that day), host available |

The host is e-mailed when `notify_host_on_check_in` is on and the host is available (budgeted).
409 and 410 refusals carry `details.visit` (the visit as it is now) and, where the scan table defines
them, `details.check_in_options`, so a client can handle a refused check-in like a refused scan:

- **404** `NOT_FOUND`; `PASS_INVALID` (QR with garbage or another visit's pass)
- **409** `VISIT_ALREADY_CHECKED_IN`, `VISIT_CANCELLED`, `VISIT_COMPLETED`, `HOST_INACTIVE`,
  `PASS_NOT_YET_VALID`, `OVERRIDE_NOT_ALLOWED`, `VISITOR_ALREADY_INSIDE`
- **410** `PASS_EXPIRED`, `PASS_REVOKED` (QR)
- **422** on `reason`
- **429** `RATE_LIMITED` (`scan_per_user` for QR; `attendance_refusals_per_user` for MANUAL and OVERRIDE)
- Audit `VISIT_CHECKED_IN` (method; `id_verified` for MANUAL/OVERRIDE) or `VISIT_CHECK_IN_REFUSED`.

#### `POST /api/v1/visits/{visit_id}/check-out` — `RECEPTION`

Body `CheckOutRequest`. **200** `Visit` (CHECKED_OUT); the active pass is revoked (`VISIT_COMPLETED`).
QR accepts any pass of this visit, including a replaced one. CORRECTED records an earlier time between
the check-in and now, with a note.

- **404** `NOT_FOUND`; `PASS_INVALID` (QR)
- **409** `VISIT_NOT_CHECKED_IN` (with `details.visit`)
- **422** on `check_out_at` ("must not be before the check-in time" / "must not be in the future"), `note`
- **429** `RATE_LIMITED` (`scan_per_user` for QR; `attendance_refusals_per_user` for MANUAL and CORRECTED)

### 10.8 Reception

#### `POST /api/v1/reception/scan` — `RECEPTION`

Body `ScanRequest`. Evaluates the pass without changing anything (apart from NO_SHOW marking). Outcomes,
in this order:

| Row | Condition | Response | `details.check_in_options` |
|---|---|---|---|
| 1 | malformed input, unknown pass, another company's pass | 404 `PASS_INVALID` | – |
| 2 | visit CANCELLED | 409 `VISIT_CANCELLED` | `[]` |
| 3 | visit CHECKED_OUT | 409 `VISIT_COMPLETED` | `[]` |
| 4 | visit CHECKED_IN | 200 `ScanResult` `ALREADY_CHECKED_IN`, `actions.check_out: true`, warning `OVERSTAYED` after `scheduled_end` | – |
| 5 | host deactivated or no longer a host | 409 `HOST_INACTIVE` | `[]` |
| 6 | pass replaced (ROTATED / VISITOR_EMAIL_CHANGED), visit SCHEDULED | 410 `PASS_REVOKED` | `["MANUAL"]` inside the window; `["OVERRIDE"]` same day outside it; else `[]` |
| 7 | visit NO_SHOW, or SCHEDULED after `window_end` | 410 `PASS_EXPIRED` | `["OVERRIDE"]` on the visit's company-local day, else `[]` |
| 8 | SCHEDULED before `window_start` | 409 `PASS_NOT_YET_VALID` | `["OVERRIDE"]` on the visit's day, else `[]` |
| 9 | SCHEDULED inside the window | 200 `ScanResult` `READY`, `actions.check_in: true`, warning `OUTSIDE_SCHEDULED_TIME` outside the scheduled times | – |

Rows 2–8 put the full `Visit` in `error.details.visit`. Every outcome is audited as `PASS_SCANNED` with
its `outcome`. **429** `RATE_LIMITED` (`scan_per_user`, counted before evaluation).

Example refusal (abridged):

```json
{
  "error": {
    "code": "PASS_EXPIRED",
    "message": "This visitor pass has expired.",
    "details": { "visit": { "id": "…", "status": "NO_SHOW", "…": "…" }, "check_in_options": ["OVERRIDE"] }
  },
  "request_id": "…"
}
```

#### `GET /api/v1/reception/today` — `RECEPTION`

**200** `ReceptionToday` for the company-local day (`date`): `expected` (SCHEDULED visits whose pass
window opens before the end of today), `inside` (every CHECKED_IN visit, any day), `checked_out`
(checked out today, latest first), `no_show` (today's visits that became NO_SHOW). Each list holds at
most 200 visits; `counts` are exact and add `cancelled` (scheduled today) and `walk_ins` (checked in
today). Poll with `X-Background-Refresh: 1`.

#### `GET /api/v1/reception/inside` — `VIEW_INSIDE`

Evacuation list: every CHECKED_IN visit whatever its day, ordered by check-in time, **never capped**.
**200** `InsideList`; each item's `visitor` adds the visitor's current `phone`.

#### `POST /api/v1/reception/check-out-stale` — `RECEPTION`

Body `StaleCheckOutRequest`. Checks out every visit that was checked in before the company-local today
**and** whose `scheduled_end` has passed, with method BULK, `check_out_at = max(check_in_at,
scheduled_end)` and the reason as note. **200** `{"checked_out": n}` (0 is a valid answer). Audit
`STALE_VISITS_CHECKED_OUT` plus one `VISIT_CHECKED_OUT` per visit.

#### `POST /api/v1/reception/walk-ins` — `RECEPTION`

Body `WalkInCreate`. Creates the visit already CHECKED_IN (method WALK_IN, `scheduled_start` = now,
`scheduled_end` = `expected_end`) **without a pass**; reuses a visitor matched by e-mail (empty fields
are filled). The host is e-mailed as for a check-in. **201** `Visit`.

- **409** `WALK_INS_DISABLED`, `VISITOR_ALREADY_INSIDE`, `VISITOR_EXISTS`
- **422** on `expected_end`, `reason` (LOST_PASS rules), `reason_note`, `host_id`, `department_id`, `visitor_id`, `visitor.*`
- **429** `RATE_LIMITED` (`attendance_refusals_per_user`)
- **503** `SERVICE_BUSY` (as for `POST /visits`)
- Audit `WALK_IN_CREATED`, `VISIT_CHECKED_IN`, or `WALK_IN_REFUSED`.

### 10.10 A company's e-mail texts

Phase 11 (B11-20 … B11-31). A company's administrators (`ADMINISTER`; every other role 403 `FORBIDDEN`)
replace, per language, some words of the seven visit e-mails. `{kind}` is one of `VISITOR_INVITATION`,
`VISIT_RESCHEDULED`, `VISIT_CANCELLED`, `HOST_ARRIVAL` and, since Phase 14 (B14-2), the host's
`HOST_VISIT_SCHEDULED`, `HOST_VISIT_RESCHEDULED`, `HOST_VISIT_CANCELLED`; any other value, `PASSWORD_RESET`,
`PASSWORD_CHANGED` and `VISITOR_CALENDAR` (it takes the invitation's words, B14-10) included, answers 404
`NOT_FOUND` (the security e-mails keep the product's words).

Editable fields (`max_length` in characters; "one line" refuses line breaks and tabs):

| Field | Kinds | Lines | Max | Required variable | Product's text (`default`) |
|---|---|---|---|---|---|
| `subject` | all | one | 150 | `company` (visitor kinds), `visitor_name` (HOST_ARRIVAL, HOST_VISIT_*); `purpose` is not allowed | the catalog subject; a visitor e-mail's subject is "<lead language> \| <other language>", each half from its own language's text |
| `heading` | all | one | 150 | | the heading |
| `greeting` | all | one | 150 | | "Hello {visitor_name}," (HOST_ARRIVAL, HOST_VISIT_*: "Hello {host_name},") |
| `intro` | all | many | 1000 | | the first paragraph |
| `button` | VISITOR_INVITATION | one | 40 | | "Open my visitor pass" |
| `closing` | all | many | 1000 | | "" (an extra paragraph when set) |
| `footer_note` | all | many | 300 | | "" (an extra footer line when set) |

Variables (the allow-list of the kind; `{name}` in a text):

| Kinds | Variables |
|---|---|
| VISITOR_INVITATION, VISIT_RESCHEDULED, VISIT_CANCELLED | `visitor_name`, `company`, `host_name`, `date`, `time` (the visit's time range), `timezone`, `department`, `purpose` |
| HOST_ARRIVAL | `host_name`, `visitor_name`, `visitor_company`, `company`, `date` (the visit's date), `time` (the check-in time), `timezone`, `purpose` |
| HOST_VISIT_SCHEDULED, HOST_VISIT_RESCHEDULED, HOST_VISIT_CANCELLED | `host_name`, `visitor_name`, `visitor_company`, `company`, `date`, `time` (the visit's time range), `timezone`, `department`, `purpose` |

Rules: plain text only; CRLF/CR become LF and white space at both ends is removed; an empty or `null`
text returns the field to the product's text. Values are escaped and kept in their own writing direction in
the e-mail; `company` and `department` are in the section's language. Everything not in the table (layout,
logo, QR code, the details, the pass link, the validity window, "This pass is personal", reply and sender
lines) is fixed. Texts are used for every e-mail rendered after they are saved.

What bounds the e-mail a company's texts can make (review, B11-40; a variable's value can be far longer
than its name):

| Rule | Value | Where it shows |
|---|---|---|
| A variable in one text | at most `max_variable_uses` (3) times | 422 `placeholder_repeated` (`name`, `max`) |
| `purpose` (free text typed for one visit) | not in a `subject` (`forbidden_variables`) | 422 `placeholder_not_allowed` (`name`) |
| A rendered subject | at most 250 characters; in a bilingual subject each language keeps at least half. A subject that is too long gives up some of the **company's name** first (UX review, B12-24): the name is cut short where it stands, with "…", to no fewer than 12 characters, so the date after it stays and each half is a whole sentence ("… | Your visit to International Company for Advanced Technological Solutions and Integrated Digital… on Wednesday, 14 October 2026", where it was "… and Integrated Digital Services on Wednesday, 14 Octo…"). Only then is it cut at its end, with "…" | every e-mail, the product's own subjects too |
| A rendered text | at most twice the field's `max_length`, values included, cut with "…" | the e-mail and the preview |
| A text saved before a rule existed | not used: the field shows the product's text | the e-mail and the preview; `override` still returns it, and saving it again is refused |

Every subject is also one line without direction controls (embeddings, overrides, isolates) and without an
RFC 2047 encoded word: `=?` is written `= ?`, for every e-mail provider (B11-41). A time range (`{time}` of a
visitor e-mail) stays on one line in the HTML part (B11-47), and a `closing` is a paragraph of its own
(B11-48).

### 10.12 A company's identity

Phase 12 (B12-1 … B12-8). Every company has a logo for light surfaces, a logo for dark surfaces, a square
icon and one colour. **Only the platform owner sets them**: the endpoints below are in the platform realm
(platform session; unsafe ones the platform CSRF token; a company session gets 401), and no endpoint of a
company's own users takes any of them. Every change answers the company's whole identity:

```json
{ "logo_url": "/api/v1/public/companies/nova-labs/brand/logo.png?v=5b0c2f9e41a7d3c6",
  "logo_dark_url": null,
  "icon_url": "/api/v1/public/companies/nova-labs/brand/icon.png?v=0e7a91b4c2d85f36",
  "color": "#7c3aed",
  "palette": { "strong": "#7c3aed", "strong_hover": "#6919d4", "deep": "#372e56", "bright": "#c0b0ff",
               "tint": "#f2f0ff", "tint_border": "#d2caf6", "on_strong": "#ffffff", "on_bright": "#1c262b",
               "surface": "#7c3aed", "on_surface": "#ffffff", "surface_hover": "#6919d4" },
  "version": "9d1f6c0a2b3e4f57" }
```

`CompanyBrand`:

| Field | |
|---|---|
| `logo_url`, `logo_dark_url`, `icon_url` | Same-origin paths of the public image endpoint ([§10.13](#1013-public-identity-endpoints)), each **with its image's own version** (`?v=`, 16 hexadecimal digits, random per upload): use them exactly as given. `null` while the company has no such image. `logo` is drawn for light surfaces, `logo_dark` for dark ones. |
| `color` | The colour the platform owner chose, `#rrggbb` in lower case, or `null` (the product's palette). |
| `palette` | `BrandPalette`, `null` exactly when `color` is. The shades are derived by the server (the only implementation; the e-mails use the same ones), so that text reads whatever colour was chosen. |
| `version` | 16 hexadecimal digits that change whenever an image, the colour or the way a palette is derived changes. For a client's own caches of the whole identity; it is **not** the `v` of an image. |

`BrandPalette`, each value `#rrggbb`, with the contrast the server guarantees for every colour (WCAG 2.x,
measured on these values):

| Role | Use | Guaranteed |
|---|---|---|
| `strong` | **text, links and icons on white**; also a surface under white text | white on it ≥ 4.5. The chosen colour itself when white already reads on it; otherwise the same hue, darker (to 5:1) |
| `strong_hover` | the hover and pressed step of `strong` | white on it ≥ 4.5; at least 0.06 of OKLCH lightness away from `strong` (darker, or lighter for a `strong` close to black) |
| `surface` *(UX review, B12-21)* | **what the brand's surfaces are painted with**: the application's shell, primary buttons, the bar and the button of an e-mail | the chosen colour **itself** whenever white or the dark ink reads on it (4.5:1); otherwise (a mid-tone that carries neither) `strong` |
| `on_surface` *(UX review)* | text and icons on `surface` and on `surface_hover` | `#ffffff` where white reads on `surface` (white is preferred), otherwise the dark ink `#1c262b` (the value of `on_bright`); it on `surface` ≥ 4.5 |
| `surface_hover` *(UX review)* | the hover and pressed step of `surface` | `on_surface` on it ≥ 4.5; at least 0.06 of OKLCH lightness away from `surface` |
| `deep` | dark surfaces | white on it ≥ 10 |
| `bright` | accents on dark surfaces, fills under dark text | `on_bright` on it ≥ 4.5; it on `deep` ≥ 4.5 |
| `tint` | chips, selected rows, notices | `strong` on it ≥ 4.5; the product's own text colours read on it |
| `tint_border` | the edge of tinted elements | decorative |
| `on_strong` | text on `strong`, `strong_hover` and `deep` | always `#ffffff` |
| `on_bright` | text on `bright` | always `#1c262b` |

A grey stays grey in every role; black, white, yellow and neon colours all give a readable palette. Always
draw with the roles, never with `color` itself.

**A company's own colour on its surfaces** (UX review, B12-21). `strong` differs from `color` whenever
white would not read on `color`: a yellow `#f5b800` has the olive brown `#8e6900` as `strong`, a pastel
`#f9c6d0` has `#90636d`, a neon `#39ff14` has `#138100`. Painting a shell or a button with `strong` made a
yellow company look brown. `surface` is the colour as it was chosen, under whichever ink reads on it:

| `color` | `surface` | `on_surface` | `surface_hover` | `strong` (text and links on white) |
|---|---|---|---|---|
| `#f5b800` yellow | `#f5b800` | `#1c262b` | `#daa300` | `#8e6900` |
| `#f9c6d0` pastel | `#f9c6d0` | `#1c262b` | `#e2b0ba` | `#90636d` |
| `#39ff14` neon | `#39ff14` | `#1c262b` | `#2ce500` | `#138100` |
| `#ffffff` white | `#ffffff` | `#1c262b` | `#e8e8e8` | `#6f6f6f` |
| `#188086` teal | `#188086` | `#ffffff` | `#006a70` | `#188086` |
| `#000080` navy | `#000080` | `#ffffff` | `#000055` | `#000080` |
| `#000000` black | `#000000` | `#ffffff` | `#292929` | `#000000` |
| `#808080` mid grey | `#6f6f6f` | `#ffffff` | `#5b5b5b` | `#6f6f6f` |
| `#ff0000` pure red | `#e00000` | `#ffffff` | `#bc0000` | `#e00000` |

- White reads on a colour whose relative luminance is at most 0.183, the dark ink on one of at least
  0.256. Between the two (a mid grey, a pure red) neither reaches 4.5:1 and `surface` is `strong`.
- Wherever `surface` is `strong` (every dark colour and every mid-tone), `on_surface` is `on_strong` and
  `surface_hover` is `strong_hover`: nothing changes for those companies.
- `surface_hover` is darker by 0.07 of OKLCH lightness wherever `on_surface` still reads on the darker
  colour; it is lighter for a colour too dark to darken visibly (black: by 0.16, to at least 0.28) and for
  a light surface that is only just light enough for the dark ink (an orange `#ff6600`: `#ff9162`). The
  least difference, measured on the values returned, is 0.06 of OKLCH lightness (three times what is
  taken as just noticeable).
- Use `strong`, not `surface`, for anything written **on white** in the brand's colour (links, icons,
  outlines): the yellow itself cannot be read there. A light `surface` may need an edge of its own on a
  white background (a white company's `surface` is white); `strong` reads on white for every colour.
- `brand.version` changed for every company with a colour when these roles were added (the derivation is
  named `oklch-2`), so a client's stored copy of a brand is replaced.

#### `GET /api/v1/platform/companies/{company_id}/brand` — platform

**200** `CompanyBrand`. **404** unknown company. A deactivated company keeps its identity and answers here.

#### `PATCH /api/v1/platform/companies/{company_id}/brand` — platform

Body `CompanyBrandUpdate` `{"color": "#7c3aed"}` or `{"color": null}` (back to the product's palette). The
key is required. **200** `CompanyBrand`. The same colour again changes and audits nothing.

- **404** unknown company
- **422** on `color`: `required` (the key is missing), `invalid_color` (anything but `#` and six
  hexadecimal digits in lower case: no upper case, no `#rgb`, no names, nothing trimmed); `not_allowed` on
  any other key
- **429** `RATE_LIMITED` (`brand_changes_per_user`)
- Audit `COMPANY_BRAND_UPDATED` `{changed_fields: ["color"]}`, with `removed_fields: ["color"]` when it
  was cleared (both trails)

#### `PUT /api/v1/platform/companies/{company_id}/brand/assets/{kind}` — platform

`{kind}` is `logo`, `logo_dark` or `icon`. **The body is the PNG file itself** with
`Content-Type: image/png` (no JSON, no multipart form), at most 524,288 bytes:

```bash
curl -sS -b "$JAR" -X PUT "$BASE/api/v1/platform/companies/$COMPANY/brand/assets/logo" \
  -H "Origin: $BASE" -H "X-CSRF-Token: $CSRF" -H "Content-Type: image/png" --data-binary @logo.png
```

**200** `CompanyBrand`, with a new address for that image. The same image again changes and audits
nothing (the address stays).

What a file must be:

| | `logo`, `logo_dark` | `icon` |
|---|---|---|
| Size in pixels | 32–1200 wide, 32–600 high | square, 192–512 |
| Format | PNG, any colour type and bit depth PNG defines (grey, palette, truecolour, with or without alpha; 1 to 16 bits) | the same |
| Refused | interlaced (Adam7) and animated (APNG) images; a damaged file (a wrong checksum, a truncated or misplaced chunk, an unknown critical chunk); **anything after the image's end**; image data that is not exactly the image the header describes | the same |

**The server never stores the file as it came.** It checks it without an image library and writes it again
from the parts that draw the image; text, colour profiles, time stamps and every other extra are dropped.
What the public endpoint serves is that rewritten file.

- **401** / **403** before any byte of the body is read
- **404** unknown company, or a `{kind}` other than the three
- **408** `BAD_REQUEST` when the body is not complete 30 seconds after the request reached the API
  ("The upload did not arrive in time. Please try again."). A deployment's nginx passes this one body on
  while it arrives, so the API reads it from the client's own connection
- **413** `PAYLOAD_TOO_LARGE` above 524,288 bytes (from nginx in a deployment, in the same envelope)
- **415** `UNSUPPORTED_MEDIA_TYPE` for a `Content-Type` other than `image/png` (parameters and letter case
  are ignored; the header only opens the door, the bytes are what is judged)
- **422** on `file`: `required` (an empty body), `invalid_image`, `image_too_small`
  `{min_width, min_height}`, `image_too_large` `{max_width, max_height}`, `image_not_square`
- **429** `RATE_LIMITED` (`brand_changes_per_user`: every attempt counts, refused files included)
- **503** `SERVICE_BUSY` from nginx, with `Retry-After: 5`, when eight uploads are already in progress
  on the site or four from the caller's address; and from the API when the file could not be checked
  within two seconds because two others were being checked. Removing an image (`DELETE`, below) is never
  refused for uploads in progress
- Audit `COMPANY_BRAND_UPDATED` `{changed_fields: ["<kind>"]}` (both trails): never the image or its size

#### `DELETE /api/v1/platform/companies/{company_id}/brand/assets/{kind}` — platform

Removes the image. **200** `CompanyBrand` with that address `null`; removing what is not there changes and
audits nothing. **404**; **429** (`brand_changes_per_user`). Audit `COMPANY_BRAND_UPDATED`
`{changed_fields: ["<kind>"], removed_fields: ["<kind>"]}`. The image's public address answers 404 from
then on.

#### `POST /api/v1/platform/brand/palette` — platform

Body `BrandPaletteRequest` `{"color": "#ffd400"}`. **200** `BrandPalette`: the palette that colour would
give a company. Nothing is saved, no company is named, nothing is audited, and it takes no slot of the
budget of brand changes. **422** on `color` (`required`, `invalid_color`).

#### A company's e-mail texts, for the platform owner

`GET /api/v1/platform/companies/{company_id}/email-templates`, `GET` and `PATCH …/{kind}`,
`POST …/{kind}/reset`, `POST` and `GET …/{kind}/preview`, `POST …/{kind}/test`: the seven endpoints of
[§10.10](#1010-a-companys-e-mail-texts) for the company in the path, on the same service: the same bodies,
answers, checks, field codes and limits. What differs:

- they need a platform session; a company's administrator has them under `/email-templates`;
- **404** for an unknown company (a body that breaks a text rule answers its 422 first, as every body
  check does);
- the texts are the company's: its administrators read what the platform owner saved and may change it
  again. No user of the company is recorded beside a text the platform owner saved; the audit rows say
  who did;
- a change is audited in both trails (`EMAIL_TEMPLATE_UPDATED`, `EMAIL_TEMPLATE_RESET`), the company's row
  without an actor, with `source: "platform"` and `platform_admin_id`, and without address or browser;
- **the test e-mail goes to the platform owner's own address** (`{"sent_to": "<the platform account's
  address>"}`), never to anyone of the company: five an hour per platform account
  (`template_test_sends_per_user`), apart from every administrator's budget. Audit
  `EMAIL_TEMPLATE_TEST_SENT` (both trails);
- the preview's sample host is a sample name («عمر خليل» / "Omar Khalil"), not a person of the company;
- previews and tests show the company's own e-mail: its logo, colours and sender name.

### 10.13 Public identity endpoints

Phase 12 (B12-9, B12-10). What a company's sign-in page and a visitor's pass page read **before anyone
signs in**: how an active company is named, its language and its identity. Addressed by the company's
slug; no session, no cookie read, none set; a signed-in person, the platform owner and a stranger get the
same bytes.

- **Active companies only, and one 404.** A slug nobody has, a deactivated company, a string no slug could
  be, a company without that image and an image name that does not exist all answer the same
  `404 NOT_FOUND`. Slugs are compared as they are (never folded to lower case).
- **Nothing else is public**: no ID, time zone, address, state or count of a company.
- **Counted.** Every request takes a slot of the client's budget (600 a minute per address, 6,000 per
  IPv6 /48) before anything is looked up: **429** `RATE_LIMITED` with `Retry-After` beyond it.
- **Cacheable.** Successful answers say how long they may be kept (below) and carry a strong `ETag` (the
  quoted SHA-256 of the body). A request with `If-None-Match` naming it (a list, `W/` and `*` are read as
  RFC 9110 says) gets **304** with the same `ETag` and `Cache-Control` and no body. Errors are `no-store`.
  No answer depends on a request header, so there is no `Vary`.

#### `GET /api/v1/public/companies/{slug}/brand` — public

**200** `PublicCompanyBrand`, `Cache-Control: no-cache` (kept, and checked with the server every time):

```json
{ "slug": "nova-labs", "name": "Nova Labs", "name_ar": "نوفا لابز", "default_language": "ar",
  "brand": { "logo_url": "/api/v1/public/companies/nova-labs/brand/logo.png?v=5b0c2f9e41a7d3c6",
             "logo_dark_url": null, "icon_url": null, "color": null, "palette": null,
             "version": "3fd0a51c77e2b894" } }
```

#### `GET /api/v1/public/companies/{slug}/brand/{kind}.png` — public

`{kind}` is `logo`, `logo_dark` or `icon`. Query `v?` (the image's version, at most 64 characters; any
other parameter is a 422). **200**, `Content-Type: image/png`, the PNG as the server wrote it.

| Request | `Cache-Control` |
|---|---|
| `v` is the image's **current** version (the addresses a `CompanyBrand` carries) | `public, max-age=31536000, immutable`: a new image has a new address, so this one never shows other bytes |
| no `v`, an older one, a made-up one | `public, max-age=60`: the current image, briefly, so no address can be filled with other bytes ahead of time and an old link heals within a minute |

`v` selects nothing: the image is always the current one. The answer carries the API's headers
([§11](#11-response-headers)) and a policy that runs and loads nothing wherever the image is opened:
`Content-Security-Policy: default-src 'none'; sandbox; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`.

#### `GET /api/v1/public/companies/{slug}/manifest.webmanifest` — public

**200**, `Content-Type: application/manifest+json`, `Cache-Control: no-cache`: the company's web app
manifest.

```json
{ "id": "/c/nova-labs", "name": "نوفا لابز للحلول الرقمية", "short_name": "نوفا لابز",
  "description": "تسجيل الزوار ودعواتهم واستقبالهم", "lang": "ar", "dir": "rtl",
  "start_url": "/c/nova-labs", "scope": "/", "display": "standalone", "orientation": "any",
  "background_color": "#f2f0ff", "theme_color": "#7c3aed",
  "icons": [ { "src": "/api/v1/public/companies/nova-labs/brand/icon.png?v=0e7a91b4c2d85f36",
               "sizes": "512x512", "type": "image/png", "purpose": "any" } ] }
```

`name` is the company's name in its default language (`name` when it has no Arabic one), in full.
`short_name` (UX review, B12-25; it was the whole name) is that name while it has at most 12 characters;
otherwise as many of its first words as fit in 12, without the sign or the small word that only joined
them to the rest ("Bank of America Corporation" → "Bank", «مركز نبض الطبي» → «مركز نبض»), and the first 12
characters where no word boundary serves ("International Company …" → "Internationa"). It has no ellipsis
and never ends inside a character. `theme_color` and `background_color` are `palette.surface` (UX review,
B12-21: the colour of the application's shell; it was `palette.strong`) and `palette.tint`, or the
product's `#188086` and `#f1f1f1` while the company has no colour; `icons` holds the company's icon with
its real size, and is **empty while it has none**. Nothing in it names the product.

## 11. Response headers

Every API response:

| Header | Value |
|---|---|
| `X-Request-ID` | 32 hex characters (or the ID set by a trusted proxy) |
| `Cache-Control` | `no-store` (the successful answers of the public identity endpoints set their own: `no-cache`, `public, max-age=60` or `public, max-age=31536000, immutable`, [§10.13](#1013-public-identity-endpoints)) |
| `ETag` | only on the successful answers of the public identity endpoints: the quoted SHA-256 of the body |
| `Content-Security-Policy` | `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` (the e-mail preview documents have their own sandboxing policy, [§10.10](#1010-a-companys-e-mail-texts); a public brand image has `default-src 'none'; sandbox; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`) |
| `Cross-Origin-Resource-Policy` | `same-origin` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` (`SAMEORIGIN` on the e-mail preview documents) |
| `Referrer-Policy` | `no-referrer` |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` (only when `APP_ENV=production`) |
| `Retry-After` | on 429 (seconds) |

No `Server` header is sent. nginx does not compress API responses (they can mix one-time links with
reflected input), adds no caching rule of its own to them and keeps no copy: what the API says about
caching is what the client receives.
